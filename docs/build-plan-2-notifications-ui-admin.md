## Срез 7 — Уведомления (in-app центр + Web Push)

### Зачем (ценность)
Житель узнаёт об объявлении/смене статуса заявки **без захода в приложение** — меньше звонков
председателю (features.md §0.3). Председатель мгновенно видит новые заявки (§0.2).

### Архитектура (решения)
1. **Два слоя, строим в этом порядке:**
   - **In-app центр уведомлений** (колокольчик + лента) — БД-надёжный слой, работает у всех,
     включая iOS до установки PWA. Push — надстройка над ним.
   - **Web Push** (`web-push` npm, VAPID) — доставка на устройство при закрытом приложении.
2. **Схема данных (2 таблицы):**
   - `Notification` — **tenant, под RLS** (osiId, userId, type, title, body, entityType/entityId,
     readAt, createdAt). Новая tenant-таблица → добавить в RLS-миграцию (ENABLE+FORCE+policy,
     prisma/README.md «Как добавлять новые модели»).
   - `PushSubscription` — **identity, вне RLS** (userId, endpoint UNIQUE, p256dh, auth,
     userAgent, createdAt). Подписка принадлежит устройству пользователя, не ОСИ.
3. **🔴 Data residency (NFR-001/051):** payload web push проходит через FCM/Mozilla autopush
   (серверы вне РК). Поэтому **в payload — ноль ПДн и ноль содержимого**: только
   `{ type, notificationId }` + нейтральный титул («Новое уведомление в ОСИ»). Текст
   подтягивается из нашего API при открытии. Зафиксировать как **REQ-105**.
4. **Custom service worker:** `customWorkerSrc` (@ducanh2912/next-pwa) → `service-worker/index.ts`
   с обработчиками `push` и `notificationclick` (deep link на `/app?n=<id>`). Плагин сам вшивает
   его в sw.js — паттерн из официального примера `examples/web-push`.
5. **Fan-out — инлайн, без очереди** (NFR-010): `Promise.allSettled` по подпискам получателей;
   `410 Gone` → удаляем мёртвую подписку. Очередь (BullMQ+Redis) — осознанно НЕ сейчас;
   пересмотреть при >1000 получателей на событие.
6. **Триггеры (серверные, в сервисах comms):**
   | Событие | Получатели |
   |---|---|
   | Объявление опубликовано | жители дома (Occupant→User) |
   | Заявка создана | председатели ОСИ |
   | Статус заявки изменён | автор заявки |
   | Сообщение в тред | «противоположная сторона» треда |
7. **VAPID-ключи:** `WEB_PUSH_EMAIL`, `WEB_PUSH_PRIVATE_KEY` (секрет), `NEXT_PUBLIC_WEB_PUSH_PUBLIC_KEY`
   — в `.env` (+ example с плейсхолдерами), генерация `npx web-push generate-vapid-keys`.
8. **Настройки пользователя:** один тумблер «Push-уведомления» в профиле (гранулярность — потом).

### Новые требования (добавить в functional.md ДО кода)
- **REQ-100** [MUST] — In-app центр уведомлений: колокольчик со счётчиком непрочитанных, лента, отметка прочтения.
- **REQ-101** [MUST] — События-триггеры по таблице выше.
- **REQ-102** [MUST] — Подписка/отписка Web Push из профиля; permission запрашивается по жесту пользователя, не на загрузке.
- **REQ-103** [MUST] — Мёртвые подписки (404/410) удаляются автоматически.
- **REQ-104** [SHOULD] — Тумблер push в профиле.
- **REQ-105** [MUST] — Payload push не содержит ПДн/содержимого (data residency, NFR-051).

### План работ
1. Спека: REQ-100..105 в functional.md; миграция `notifications` (+RLS-политика для `notification`).
2. `src/lib/notifications/service.ts`: `notify(osiId, userIds, {...})` — создаёт Notification
   (forTenant) + push fan-out; `src/lib/notifications/push.ts` — web-push обёртка.
3. Вызовы notify() из comms/service.ts (4 триггера).
4. API: `GET /api/notifications`, `POST /api/notifications/read`, `POST /api/push/subscribe`,
   `DELETE /api/push/subscribe`.
5. UI: колокольчик в шапке `/app`, лента, тумблер в профиле; `service-worker/index.ts`.
6. Тесты: unit (адресация fan-out по ролям), integration (RLS-изоляция Notification),
   e2e (объявление → колокольчик жителя +1 → прочтение). Push — ручная проверка (skill `verify`).

### DoD среза 7
- e2e: событие → уведомление в центре второго пользователя → отметка прочтения.
- Integration: Notification изолирован по ОСИ (deny-by-default).
- Push приходит на реальный браузер (ручная проверка через preview), payload без ПДн (REQ-105).
- Отписка/410 чистит подписку. Все гейты зелёные.

## Срез 8 — UI/UX: дизайн-система, интерфейс председателя и жителя

### Зачем
«Дифференциатор — удобство» (features.md §0) — сейчас интерфейс функциональный, но грубый
(inline-стили, нет навигации, нет переключателя ОСИ). Это продукт, а не полиш.

### Архитектура (решения)
1. **Tailwind CSS v4** (`tailwindcss` + `@tailwindcss/postcss`, `@import "tailwindcss"` +
   `@theme`): существующие CSS-переменные (--brand и т.д.) переносятся в `@theme` — тёмная тема
   сохраняется. Обоснование: утилиты вместо разрастающихся inline-стилей, mobile-first из
   коробки, zero-runtime. **Без тяжёлых UI-китов** (NFR-010) — свой набор из ~10 компонентов:
   `Button, Card, Input, Select, Textarea, Badge, Tabs, EmptyState, Skeleton, Sheet`.
2. **Мокапы ДО вёрстки** (visualize MCP) — согласовать направление на трёх ключевых экранах,
   потом верстать. Дешевле итерации.
3. **Навигация:**
   - **Житель:** нижний таб-бар — `Главная (лента) · Заявки · Инфо · Профиль`. Лента =
     объявления + статусы заявок одним списком (меньше кликов, §0.5).
   - **Председатель:** шапка с **переключателем ОСИ (REQ-004 — сейчас нет в UI!)** +
     дашборд-сводка (новые заявки, охват прочтения, дома) → экран дома с табами
     `Квартиры · Объявления · Заявки · Инфо`.
4. **Состояния:** empty-state с действием, skeleton при загрузке, offline-бейдж (PWA),
   оптимистичные отметки прочтения.
5. **A11y (WCAG 2.1 AA):** сохранить текущую базу (label/htmlFor, role=alert, focus-visible),
   добавить aria-current в табах, контраст токенов проверить в тёмной теме.

### План работ
1. Мокапы 3 экранов (visualize) → согласование → фикс в `docs/specs/ui-design.md` (кратко:
   токены, навигация, паттерны состояний).
2. Tailwind v4 setup (postcss.config.mjs, globals.css `@theme`), компоненты `src/components/ui/`.
3. Житель: таб-бар, лента, экраны заявок/инфо/профиля (профиль: телефон, квартира, тумблер push).
4. Председатель: шапка + переключатель ОСИ, дашборд, экран дома (табы), полировка форм.
5. Лендинг + логин в новом стиле.
6. e2e-регресс (обновить селекторы), скриншоты мобильного вьюпорта (Claude Preview MCP:
   preview_start → resize mobile → screenshot, светлая+тёмная).

### DoD среза 8
- Все существующие e2e зелёные после редизайна (регресс — главный риск).
- Переключатель ОСИ работает (e2e: председатель двух ОСИ видит разные дома).
- Скриншот-проверка на mobile (375px) и desktop, светлая+тёмная темы.
- 0 inline-стилей в новых экранах; a11y-проходка клавиатурой.

## Срез 9 — Админ-панель (SuperAdmin)

### Зачем
Платформа продаётся по подписке (B2B2C): нужен инструмент владельца — управлять ОСИ,
подписками, аккаунтами председателей, видеть статистику. Сейчас SuperAdmin-роль есть в модели,
но интерфейса и bypass-пути нет.

### Архитектура (решения) — сначала ADR-0008!
1. **ADR-0008 «Кросс-тенантный админ-доступ»:** отдельный Prisma-клиент `adminPrisma` на роли
   `app_superadmin` (BYPASSRLS, создана RLS-миграцией), строка подключения — отдельный env
   `ADMIN_DATABASE_URL`. Клиент живёт ТОЛЬКО в `src/lib/admin/`, импорт из обычного кода
   запрещён (ESLint `no-restricted-imports`). Каждый вызов пишет в `AuditLog`.
2. **Доступ:** `/admin/**` — отдельный layout; guard `superAdminContext()` (роль SUPERADMIN
   хотя бы в одной записи UserOsiRole + email+пароль вход). Вся серверная (REQ-003).
   Rate-limit логина уже есть (security-review). Опционально: nginx `location /admin` с
   `allow/deny` по IP — задокументировать в README, не хардкодить.
3. **Скоуп MVP-админки (по user-roles.md §2):**
   - Дашборд: счётчики (ОСИ, дома, квартиры, жители, активные заявки) — живая статистика платформы.
   - Список ОСИ: поиск, карточка ОСИ (дома, председатели, статистика).
   - **Подписки** (REQ-070/071): статус на дом (TRIAL/ACTIVE/PAST_DUE/CANCELED), смена статуса,
     период. Ограничение при PAST_DUE — только председателю, read-доступ жителя не блокируется
     (допущение REQ-071 в functional.md).
   - **Аккаунты председателей:** создать (email+временный пароль), сбросить пароль, привязать к
     ОСИ. Это закрывает «провижининг после продажи» — дополнение к self-service Q-051.
   - Superadmin-сид: `scripts/seed-superadmin.ts` (email+пароль из env, не в репо).
4. **Вне скоупа среза:** биллинг-платежи, метрики использования, импперсонация («войти как
   председатель») — отдельное решение, риски аудита.

### Новые требования
- **REQ-110** [MUST] — /admin доступен только SUPERADMIN; все операции журналируются в AuditLog.
- **REQ-111** [MUST] — CRUD подписок на дом со статусами и периодом.
- **REQ-112** [MUST] — Создание/сброс аккаунта председателя с привязкой к ОСИ.
- **REQ-113** [SHOULD] — Дашборд-статистика платформы.

### План работ
1. ADR-0008 + `docs/specs/admin-panel.md` (краткая: экраны, права, аудит) + REQ-110..113.
2. `adminPrisma` + env + ESLint-ограничение импорта + audit-обёртка.
3. API `/api/admin/**` (osi list/detail, subscriptions, chairmen) + guard.
4. UI `/admin` (на компонентах среза 8, desktop-first — админом пользуемся мы).
5. Тесты: unit (guard), integration (adminPrisma видит все ОСИ, обычный prisma — нет; аудит
   пишется), e2e (вход суперадмина → смена статуса подписки).
6. **Обязательно `/security-review` перед мержем** — BYPASSRLS-код.

### DoD среза 9
- Не-SUPERADMIN получает 403 на всех /admin (e2e).
- Каждая мутация в админке оставляет запись AuditLog (integration).
- adminPrisma не импортируем вне `src/lib/admin/` (ESLint падает — проверено намеренным нарушением).
- Подписки управляются end-to-end; security-review пройден.

## Порядок и оценка

```
Срез 7 (уведомления)  ~1 сессия   — независимый бэкенд+минимальный UI колокольчика
Срез 8 (UI/UX)        ~1–2 сессии — самый объёмный; колокольчик получает финальный вид здесь
Срез 9 (админка)      ~1 сессия   — на готовых компонентах среза 8
```

Порядок 7→8→9 сознательный: уведомления — приоритет ценности и независимы; редизайн вберёт
их UI; админка переиспользует дизайн-систему.

## Риски
- **e2e-регресс при редизайне** — митигируется: сохраняем data-testid при вёрстке, гоняем e2e после каждого экрана.
- **iOS web push** — работает только для установленной PWA (iOS 16.4+); in-app центр это компенсирует. В UI не обещать push на iOS без установки.
- **BYPASSRLS-утечка** — митигируется ADR-0008: изоляция модуля + ESLint + аудит + security-review.
- **Firefox/FCM недоступность у части пользователей в РК** — in-app центр как гарантированный канал.
