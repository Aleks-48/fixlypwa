# План 3: объединение приложения и сайта на единой БД

> Статус: DRAFT · Дата: 2026-07-16 · Основание: решения Рахима от 2026-07-16 (см. §1).
> Предмет: слияние `fixly` (Flutter + Supabase Cloud) и `fixlypwa` (Next.js + Prisma)
> в один продукт с одной локальной БД и одним бэкендом.

## 1. Принятые решения (2026-07-16)

| # | Решение |
|---|---|
| Р-1 | **Supabase не будет ни в каком виде** — ни Cloud, ни self-hosted. Только локальный Postgres. |
| Р-2 | **Канон — схема Prisma** (`prisma/schema.prisma`). `fixly` объединяется с `fixlypwa`. |
| Р-3 | **Интерфейс Flutter сохраняется.** Переписывается слой данных, не экраны. |
| Р-4 | **То, чего нет в `fixlypwa`, переносится** из `fixly` (звонки, AI, YOLO, карты, портфолио). |
| Р-5 | **Интерфейс к БД — расширенная админка платформы** `/admin` (ADR-0008), не сторонний GUI. |
| Р-6 | Два продукта: **сайт** и **приложение**. **PWA у сайта остаётся** (уточнено 2026-07-16). |
| Р-7 | **Порядок: сначала миграция ядра, потом остальные функции.** |
| Р-8 | **Живых пользователей в проде Supabase нет — только тестовые учётки** (Рахим, 2026-07-16). Следствия: перенос данных (ETL) **отменён**, план простоя и сброс паролей не нужны, Q-057/Q-058 закрыты. Дамп делается один раз — как справочник схемы и архив. |

### 1.1 Разграничение сайта и приложения (Р-6)

Сайт — Next.js-веб-приложение, PWA-обвязка (`@ducanh2912/next-pwa`, service worker, офлайн,
Add to Home Screen) **сохраняется** — конфликта с CLAUDE.md и `features.md` §0 нет.
Приложение — нативный Flutter. Оба ходят в один API. ADR-0013 не требуется, Q-056 закрыт.

`Master`, ADR-0009).

### 5.2 Push: два механизма, не один

`PushSubscription` — Web Push/VAPID для сайта. `user_tokens` — FCM для нативного приложения.
Это разные протоколы, свести в одну таблицу нельзя. `Notification` остаётся единой точкой,
доставка ветвится на две реализации. → ADR-0012.

### 5.3 Чего в `fixly` нет и приложение это получит

`Tariff`, `Charge` (генерация), `BankAccount`, `BankStatement`, `Expense`, `Counterparty`,
`Report` (приказ № 163), `Subscription`, `AuditLog`, `InfoItem`, `Apartment`, `Account`,
`Owner`, `Occupant`, `Meeting`. Что из этого нужно в приложении, а что только на сайте —
предмет `mobile-app.md` (§4).

## 6. Фаза 3 — авторизация

### 6.1 Транспорт

Сессии сейчас в httpOnly-cookie (`src/lib/auth/session.ts:34`). Для нативного клиента cookie
хрупки (SameSite, редиректы, время жизни). Нужен `Authorization: Bearer` поверх той же таблицы
`Session` — модель не меняется, меняется только способ передачи токена. Ревизия ADR-0005.

### 6.2 Google Sign-In и Sign in with Apple

В `fixly` они есть (`google_sign_in`, `sign_in_with_apple` в `pubspec.yaml`), в `fixlypwa` —
нет вообще. Два пути: реализовать OAuth в своём бэкенде или убрать из приложения и оставить
телефон+OTP. Важно: если оставляем Google, **App Store требует Sign in with Apple** — то есть
это не «один провайдер», а два. Оба — внешние сервисы, что стоит сверить с ADR-0003 (там речь
о хранении данных, а не об аутентификации, — но решение надо принять явно). → **Q-059**.

### 6.3 Пароли и учётки

~~Пароли не мигрируют (bcrypt Supabase ≠ scrypt ADR-0005)~~ — **вопрос снят (Р-8)**:
пользователей нет, тестовые учётки пересоздаются существующим `npm run seed`.

## 8. Фаза 5 — ~~ETL~~ ОТМЕНЕНА (Р-8)

Живых данных нет — переносить нечего. Вместо ETL: дамп-справочник (фаза 0.2), пауза проекта
Supabase (фаза 0.3), тестовые данные в новой БД — существующим `npm run seed`.

Историческая справка (почему отмена — большое облегчение): ETL требовал пяти ручных развилок —
вывод `Osi` для домов (в `fixly` модели ОСИ нет), разделение `profiles` на четыре сущности
(семь полей имени, четыре флага верификации), разделение `tasks` на `Request`/`MarketListing`
без дискриминатора, сверка денег в `invoices`/`transactions` без FK, приведение битых связей
`text`→`uuid` (`messages.task_id`, `votes.proposal_id`). Всё это снято.
