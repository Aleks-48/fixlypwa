# Функциональные требования (REQ)

> Статус: DRAFT · Версия: 0.2 · Дата: 2026-07-01
> Атомарные, проверяемые. В коде/тестах ссылаться `// REQ-XXX`.
> Большинство архитектурных вопросов закрыто (см. open-questions.md). Остаются Q-012, Q-013 —
> требуют реального образца у председателя, помечены явно ниже.

## Формат
`REQ-XXX [Приоритет: MUST/SHOULD/COULD] — Формулировка (тестируемая).`

---

## Аутентификация и доступ
- **REQ-001** [MUST] — Житель входит по телефону + OTP; председатель — email/телефон + пароль (Lucia Auth, ADR-0005).
  (Ревизия 2026-07-15: одноразовый код доставляется и на email — см. REQ-005/006; парольный
  вход председателя сохраняется.)
- **REQ-002** [MUST] — Данные разных ОСИ строго изолированы через Postgres RLS (ADR-0006).
- **REQ-003** [MUST] — Права проверяются на сервере (API), не только в UI. Матрица: user-roles.md.
- **REQ-004** [MUST] — Председатель может быть связан с несколькими ОСИ; активная ОСИ выбирается в UI и определяет RLS-контекст (Q-011).
- **REQ-005** [MUST] — (добавлено 2026-07-15) Единая форма входа: одно поле «Телефон или email»,
  тип определяется автоматически (`@` → email, иначе телефон), канал кода следует из типа.
  См. `auth-email.md`.
- **REQ-006** [MUST] — (добавлено 2026-07-15) Одноразовый код доставляется на email (главный
  канал до подключения SMS-шлюза). Письмо содержит только код (data residency, NFR-001).
  Rate-limit — как для SMS (NFR-054, REQ-091), по идентификатору и IP.
- **REQ-007** [MUST] — (добавлено 2026-07-15) Самостоятельная регистрация по email/телефону:
  первый успешный ввод кода создаёт аккаунт без ролей. Карточка «Председатель» ведёт к
  созданию ОСИ (Q-051), «Житель» — к инструкции о привязке через председателя. Председатель
  может пригласить жителя по email и/или телефону (минимум один; ревизия REQ-013).
- **REQ-008** [SHOULD] — (добавлено 2026-07-15) Запрос кода не раскрывает существование
  аккаунта: ответ одинаков для нового и существующего идентификатора.
- **REQ-009** [MUST] — (добавлено 2026-07-18, решение Рахима) Telegram-канал OTP для телефона —
  временная замена SMS-шлюза до оформления ИП/юрлица (Q-030). Привязка номера к Telegram
  ТОЛЬКО через кнопку «Поделиться номером» бота (Telegram Bot API `request_contact`) — она
  физически не может передать чужой номер, поэтому не нужен подписанный токен и не возникает
  риска угона (см. `telegram-otp.md`). Включается флагом `PHONE_OTP_CHANNEL=telegram`,
  по умолчанию — `sms` (существующее поведение не меняется).

## Управление ОСИ и структурой дома
- **REQ-010** [MUST] — Председатель создаёт/редактирует ОСИ и N домов (Osi 1:N Building).
- **REQ-011** [MUST] — Ведение списка квартир дома (создание/редактирование). Ревизия
  2026-07-18 (Q-063, excel-import.md §5): `Apartment.type` (жилое/нежилое/парковка/кладовка,
  опционально) — для будущей сверки с IncomeCategory при отчёте; поле «этаж» сознательно НЕ
  добавлено (не нужно ни для одного текущего сценария).
- **REQ-012** [SHOULD] — (ревизия 2026-07-18) Импорт **реестра помещений** из Excel —
  формат подтверждён реальной выгрузкой ОСИ (Q-012 закрыт в этой части, `excel-import.md`):
  загрузка xlsx председателем → предпросмотр распознанных строк → создание Apartment +
  Owner (собственник) + Account (лицевой счёт, реальный номер из файла, не генерируется) за
  одно действие. Парсер терпим к грязным/неполным данным (пустые ИИН/телефон — не ошибка),
  повторный импорт идемпотентен (обновляет существующие записи, не дублирует). **Границы:**
  импорт НЕ создаёт Occupant/логин жителя — это отдельное осознанное действие председателя
  (REQ-013, addResident), т.к. Owner (юридическое владение) и Occupant (пользователь
  кабинета) — разные сущности, реестр даёт только первое. Начальные сальдо долга и пеня из
  той же выгрузки — вне объёма этого REQ (Q-063, отдельное решение).
- **REQ-013** [MUST] — Раздельный учёт Owner (собственник) и Occupant (проживающий/пользователь кабинета) с привязкой к квартире.
- **REQ-151** [MUST] — (добавлено 2026-07-21) Житель без ОСИ ищет свою ОСИ по названию/адресу
  (поиск среди всех Osi, identity-уровень) и отправляет заявку на подключение — свободное поле
  «дом/квартира» вместо формальной привязки к Apartment (председатель верифицирует и привязывает
  сам). См. `docs/specs/osi-join-request.md`.
- **REQ-152** [MUST] — (добавлено 2026-07-21) Председатель получает in-app уведомление
  (REQ-100/101) о новой заявке на подключение — с контактом жителя и его пометкой.
- **REQ-153** [MUST] — (добавлено 2026-07-21) Председатель видит список активных заявок своей
  ОСИ и подключает жителя существующим способом (REQ-013, AddResidentForm — поиск/ввод
  телефона или email на карточке квартиры); заявка сама привязку не делает, только
  информирует. Председатель может отметить заявку обработанной вручную.
- **REQ-154** [MUST] — (добавлено 2026-07-21) Одна активная (PENDING) заявка на пользователя
  на одну ОСИ — повторная отправка обновляет пометку существующей, не создаёт дубль.

## Тарифы и начисления
- **REQ-020** [MUST] — Настройка тарифов по статьям: эксплуатация, целевой сбор, кап.ремонт (минимум 3).
- **REQ-021** [MUST] — Массовая генерация начислений по дому за период на основе тарифов.
- **REQ-022** [SHOULD] — Ручные/разовые корректировки начислений.
- **REQ-023** [MUST] — Статусы оплаты начисления (3 значения): открыто → частично оплачено →
  оплачено. «Просрочено» — не отдельное значение статуса, а вычисляемый признак (dueDate в
  прошлом И статус ≠ «оплачено»), может сочетаться с любым из трёх статусов (уточнено при
  ревизии, см. domain-model.md §4).
- **REQ-024** [MUST] — (добавлено при ревизии) Учёт задолженности ведётся раздельно по статьям
  тарифа (эксплуатация/целевой сбор/кап.ремонт) — переплата по одной статье не может закрывать
  долг по другой (кап.ремонт — обособленный фонд, см. glossary.md). Статья платежа —
  обязательное поле, указывается председателем вручную при вводе; авто-распределение не
  делается в MVP (Q-032 закрыт, см. domain-model.md §1).
- **REQ-025** [MUST] — (добавлено после разбора формы отчёта) Реестр расходов ОСИ: сумма, дата,
  категория (по строкам 7.1.1–7.6 формы), контрагент (наименование, БИН/ИИН), назначение,
  привязка к банковскому счёту, признак «перевод собственных средств» (не доход/расход).
  Обязателен для блока «Расходы» отчёта (REQ-041b). См. report-spec.md, domain-model.md.
- **REQ-026** [MUST] — (добавлено после разбора формы отчёта) Учёт банковских счетов ОСИ
  (минимум: текущий + сберегательный) и их остатков на дату отчёта. Обязателен для блока
  «Остатки» (REQ-041a). Расходование сберегательного счёта (кап.ремонт) — только по решению
  собрания (сноска формы).

## Платежи и задолженность
- **REQ-030** [MUST] — Ручной ввод платежа по лицевому счёту (эквайринг вне MVP — см. vision.md).
- **REQ-031** [MUST] — Расчёт баланса/задолженности как Σ начислений − Σ платежей (вычисляемое значение, не хранится).
- **REQ-032** [COULD] — Импорт банковской выписки. Формат — Q-012, открыт.
- **REQ-033** [SHOULD] — (добавлено 2026-07-14) Житель может инициировать оплату своего текущего
  долга онлайн через симулятор эквайринга (демо-режим, без реального банка) — см.
  `payments-online.md`, ADR-0010. Не отменяет REQ-030: реальный эквайринг остаётся вне MVP.
- **REQ-034** [MUST] — (добавлено 2026-07-14) Онлайн-оплата идемпотентна: сумма к списанию
  пересчитывается на сервере в момент оплаты (не принимается от клиента); повторный вызов при
  уже погашенном долге — no-op, а не повторное списание.
- **REQ-035** [MUST] — (добавлено 2026-07-14) UI онлайн-оплаты явно предупреждает пользователя,
  что приложение работает в демонстрационном режиме и ввод реальных банковских реквизитов не
  требуется.
- **REQ-036** [SHOULD] — (добавлено 2026-07-14, ревизия после code review) Симулятор эквайринга
  может случайно вернуть отказ («недостаточно средств», демо-реалистичность) — отказ не изменяет
  данные (баланс/начисления не трогаются). Дополнительно: если сумма долга изменилась между тем,
  как жителю показали кнопку «Оплатить X ₸», и фактическим вызовом (например, председатель успел
  провести другой платёж), сервер отклоняет вызов явной ошибкой вместо тихого списания другой
  суммы — см. `payments-online.md` §4.

## Отчёты (ключевая фича)
- **REQ-040** [MUST] — Генерация месячного отчёта по дому за период одним действием.
- **REQ-041** [MUST] — Отчёт соответствует утверждённой форме (4 блока: остатки на счетах,
  задолженность, поступления, расходы). Полная структура и юр. источник — в `report-spec.md`.
  ⚠️ Юр. источник **исправлен**: не V2000020247 (утратил силу 12.09.2025), а V2000020283 в ред.
  приказов № 362/№ 380 — сверить актуальную редакцию перед реализацией (Q-034).
- **REQ-041a** [MUST] — Блок «Остатки» требует учёта банковских счетов ОСИ (текущий +
  сберегательный) и их остатков — см. REQ-026.
- **REQ-041b** [MUST] — Блок «Расходы» требует реестра расходов с контрагентами и категориями
  (строки 7.1.1–7.6 формы) — см. REQ-025. Без него отчёт неполон и юридически невалиден.
- **REQ-041c** [MUST] — Блок «Поступления» разбивается на категории 6.1–6.7 (взносы жителей,
  парковки/кладовки, кап.ремонт, аренда, целевые, иные), не только взносы жителей.
- **REQ-042** [MUST] — Вывод отчёта. **Точный формат вывода (PDF/веб/оба), вёрстка — Q-013**;
  структура полей известна (report-spec.md), остаётся формат представления и сверка актуальной
  редакции формы. Язык — казахский обязателен (REQ-081).
- **REQ-043** [SHOULD] — Публикация отчёта жителям в их кабинете — доступен весь отчёт дома (не только свои данные).
- **REQ-044** [SHOULD] — Формирование отчёта укладывается в целевое время (< 5 мин весь флоу — из vision.md).

## Кабинет жителя

- **REQ-051** [SHOULD] — Житель видит полный отчёт своего дома.
- **REQ-052** [MUST] — (добавлено при ревизии) «Свои начисления» (REQ-050) определяются как

  валидации на реальных председателях (не блокирует реализацию).

## Уведомления (срез 7 · build-plan-2)
- **REQ-100** [MUST] — In-app центр уведомлений: колокольчик со счётчиком непрочитанных,
  лента уведомлений, отметка о прочтении. Хранение — таблица `Notification` (tenant, под RLS).
- **REQ-101** [MUST] — События-триггеры создают уведомления адресно: объявление → жителям дома;
  новая заявка → председателям ОСИ; смена статуса заявки → автору; сообщение в тред → другой стороне.
- **REQ-102** [SHOULD] — Web Push: подписка/отписка из профиля; разрешение браузера запрашивается
  по явному жесту пользователя (тумблер), не на загрузке страницы.
- **REQ-103** [MUST] — Мёртвые push-подписки (ответ шлюза 404/410 Gone) удаляются автоматически.
- **REQ-104** [SHOULD] — Тумблер «Push-уведомления» в профиле жителя/председателя.
- **REQ-105** [MUST] — Payload web push НЕ содержит ПДн и содержимого уведомления (только тип и id):
  доставка идёт через FCM/autopush (серверы вне РК), текст подтягивается из нашего API при открытии
  (data residency — NFR-001/051).
- **REQ-106** [MUST] — (добавлено 2026-07-17, запрос Рахима) Массовая генерация начислений
  (REQ-021) создаёт уведомление жителям квартиры: одно уведомление на квартиру за прогон с
  суммарной суммой за период (не по одному на каждое начисление статьи — иначе 3 тарифа = 3
  уведомления за одно и то же начисление). Повторный (идемпотентный) прогон, не создавший новых
  начислений для квартиры, уведомление не шлёт. Квартира без жителей — пропускается молча.

## AI-ассистент (срез 30, docs/specs/ai-assistant.md)
- **REQ-155** [MUST] — Ассистент отвечает на вопросы жителя о его начислениях/платежах/
  заявках/объявлениях через tools поверх существующих сервисов под RLS; чужие данные
  недостижимы by construction (buildingId/osiId/userId берутся из сессии, не из аргументов модели).
- **REQ-156** [MUST] — Ассистент председателя: финансовая сводка дома, должники (только номер
  квартиры и сумма — без ФИО), открытые заявки.
- **REQ-157** [MUST] — Прямые идентификаторы физлиц (ФИО, телефон, email, ИИН, лицевые счета)
  не передаются внешнему LLM-провайдеру: псевдонимизация/скраббер входа (`pseudonymizer.ts`) +
  запрет полей на уровне tools (инструменты не выбирают их из БД вовсе). Хранение диалогов —
  в псевдонимизированном виде (`AssistantMessage.content`).
- **REQ-158** [MUST] — Все tools MVP read-only; действия (создать заявку и т.п.) совершает
  пользователь явной кнопкой из черновика, не модель.
- **REQ-159** [SHOULD] — Ответы по нормативке опираются на корпус документов с указанием
  источника/статьи (срез 30b, не реализовано в 30a).
- **REQ-160** [MUST] — Лимиты: `ASSISTANT_MAX_MESSAGES_PER_DAY_USER`/`_OSI` (дневной счётчик
  по `AssistantMessage`, durable — работает при нескольких инстансах); согласие пользователя
  при первом открытии чата (чекбокс); дисклеймер «не юридическая консультация» в UI.
  > Провайдер (Groq/Claude) — конфигурация `LLM_PROVIDER`, не код (docs/specs/ai-assistant.md
  > §3/§4). Смена провайдера не влияет на выполнение этих REQ — псевдонимизация и лимиты
  > реализованы на уровне оркестрации (`service.ts`/`rateLimit.ts`), не привязаны к SDK.

## Подписка / биллинг
- **REQ-070** [SHOULD] — Учёт статуса подписки на дом (trial/active/past_due/canceled), единица — Building.
- **REQ-071** [COULD] — Ограничение доступа при неоплаченной подписке.
  > ⚠️ ДОПУЩЕНИЕ (добавлено при ревизии): «ограничение доступа» должно ограничивать только
  > **председателя** (управление домом) при past_due. Житель дома не является плательщиком
  > подписки (B2B2C, ADR-0001) и обязан по закону РК видеть публикуемый отчёт (glossary.md
  > «Юридическая база») независимо от статуса оплаты председателя — read-доступ жителя не
  > должен блокироваться неоплатой подписки. Уточнить при проектировании биллинг-спеки.
