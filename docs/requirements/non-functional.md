# Нефункциональные требования (NFR)

> Статус: DRAFT · Версия: 0.1 · Дата: 2026-07-01
> Ограничения качества. Некоторые — жёсткие (data residency), некоторые — целевые [TBD].

## Data residency (жёсткое)
- **NFR-001** [MUST] — Данные физически хранятся на территории РК. Managed-облака (Supabase/Vercel/AWS) исключены. → ADR-0003.
- **NFR-002** [MUST] — VPS/хостинг — у казахстанского провайдера. Конкретный провайдер — [TBD Q-022, отложено до предпродакшн-этапа].

## Простота и поддержка
- **NFR-010** [MUST] — Монолит, минимум разных технологий; разработка и поддержка одним человеком. → ADR-0002.
- **NFR-011** [MUST] — Развёртывание одной командой `docker-compose up`.

## Масштабируемость
- **NFR-020** [SHOULD] — Возможность горизонтального масштабирования (несколько инстансов Next.js за балансировщиком + PgBouncer) без переписывания. → ADR-0002.
- **NFR-021** [TBD] — Целевая нагрузка: число ОСИ/домов/квартир на инстанс — [TBD Q-031, не блокирует MVP, оценить при первых клиентах].

## Безопасность и ПДн
- **NFR-050** [MUST] — HTTPS обязателен (Let's Encrypt через **Nginx**, решено — ADR-0002).
- **NFR-051** [MUST] — Хранение ПДн (ФИО, ИИН, контакты) — электронно, на серверах/ЦОД на территории РК (Закон РК №94-V, согласуется с NFR-001/ADR-0003). При базе >100k записей — обязательна идентификация/аутентификация пользователей БД. См. glossary.md «Юридическая база». ⚠️ Требует финальной проверки юристом перед коммерческим запуском.
- **NFR-052** [MUST] — Изоляция данных тенантов — Postgres RLS. → REQ-002, ADR-0006 (Accepted).
- **NFR-053** [SHOULD] — Хранение паролей/секретов по best practices (хеширование, .env вне репо).
- **NFR-054** [MUST] — (добавлено при ревизии) Rate limiting на OTP-эндпоинтах: лимит запросов
  кода по номеру телефона и по IP, cooldown между повторными отправками, ограниченное число
  попыток ввода кода, TTL кода. Обоснование: SMS платные (внешний шлюз, ADR-0005) — без лимита
  риск SMS-pumping/toll fraud за счёт бюджета проекта, отдельно от риска подбора кода.
- **NFR-055** [MUST] — (добавлено при ревизии) Неизменяемый (append-only) журнал изменений
  финансовых сущностей (`Charge`, `Payment`, `Tariff`) — кто/когда/что изменил. Обоснование:
  ключевая ценность продукта — прозрачность и снятие споров о деньгах (vision.md §3); без
  журнала система не может подтвердить ни одну из сторон спора о задним числом изменённом
  начислении. См. `AuditLog` в domain-model.md.

## Надёжность и бэкапы
- **NFR-060** [MUST] — Автоматический `pg_dump` по крону **ежедневно**, ротация **30 дней**, хранение на территории РК (тот же/другой провайдер).
  > ⚠️ ДОПУЩЕНИЕ (уточнено при ревизии): «тот же/другой провайдер» размывает требование —
  > хранение бэкапа **только на том же VPS**, что и рабочая БД, не считается бэкапом (потеря
  > диска = потеря и данных, и резервной копии). Требуется хотя бы одна offsite-копия
  > (другой сервер/провайдер, но по-прежнему на территории РК — NFR-001).
- **NFR-063** [MUST] — (добавлено при ревизии) Дампы БД содержат ПДн (ФИО, ИИН, контакты —
  см. NFR-051) → должны храниться в зашифрованном виде (напр. `pg_dump` + шифрование архива
  перед выгрузкой на offsite-хранилище).
- **NFR-061** [SHOULD] — Проверяемое восстановление из бэкапа (периодический тестовый restore).
- **NFR-062** [TBD] — Целевая доступность (SLA) — [TBD, не блокирует MVP].
