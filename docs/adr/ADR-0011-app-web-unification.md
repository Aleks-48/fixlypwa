# ADR-0011: Объединение приложения (fixly) и сайта (fixlypwa) на единой БД

- **Статус:** Accepted
- **Дата:** 2026-07-16
- **Контекст решения:** решения Рахима 2026-07-16, `docs/build-plan-3-unification.md`

## Контекст и проблема

Помимо `fixlypwa` (этот репозиторий) существует второй, независимо разработанный проект —
Flutter-приложение `fixly` (`C:\Projects\fixly`), реализующее почти тот же домен ОСИ
(дома, объявления, голосования, заявки, деньги, маркетплейс мастеров) на другом стеке:
Supabase Cloud (Postgres + Auth + Realtime + Storage) вместо self-hosted Postgres + Prisma.

Это прямо противоречит ADR-0003 (data residency в РК — managed-облака вроде Supabase исключены)
и создаёт два источника истины для одного домена. Нужно решить, что становится каноном и как
приложение получает данные.

## Рассматриваемые альтернативы

1. **Prisma-схема этого репозитория — канон**, `fixly` переезжает на её API, Supabase
   выбрасывается полностью.
2. **Self-hosted Supabase на VPS в РК** — Supabase Cloud заменяется на self-hosted инстанс,
   обе кодовые базы адаптируются под него.
3. **Две БД + сервис синхронизации** — `fixlypwa` и `fixly` остаются на своих БД, данные
   реплицируются между ними.
4. **Схема `fixly` — канон**, `fixlypwa` переезжает на неё.

## Сравнение (за / против)

| Критерий | 1. Prisma-канон | 2. Self-hosted Supabase | 3. Sync-сервис | 4. Схема fixly — канон |
|---|---|---|---|---|
| Data residency (ADR-0003) | ✅ уже выполнено | ✅ достижимо | ✅/⚠️ зависит от какой БД реплика | ✅ достижимо |
| Простота (NFR-010, 1 разработчик) | высокая — 1 БД, монолит уже есть | низкая — Studio/Auth/Realtime/Storage = ~5 доп. сервисов | низкая — третья система, конфликт-резолюшн | средняя |
| Целостность схемы | высокая — нормализована, есть FK, RLS, тесты | наследует все дефекты схемы fixly | худшая — два источника истины постоянно | низкая — 0 FK на `invoices`, битые `text`→`uuid` связи, 7 полей имени в `profiles` |
| Совместимость с ADR-0004/0005/0006 | не меняются | отменяет все три (Prisma, свои сессии, RLS-паттерн) | сохраняет оба независимо | отменяет все три |
| Готовность отчёта по приказу №163 (ключевой аргумент продажи, CLAUDE.md) | уже реализован | нет, пришлось бы переносить | зависит | нет, пришлось бы переносить с нуля |
| Объём работы | перенос UI-слоя Flutter (256 вызовов) | перенос инфраструктуры + всё из варианта 1 | двойная поддержка навсегда | перенос всей бэкенд-логики fixlypwa |

## Решение

**Вариант 1: Prisma-схема `fixlypwa` — единственный канон.** Supabase (Cloud и self-hosted)
исключается полностью. `fixly` сохраняет UI/UX, но полностью переходит на REST/SSE API
`fixlypwa` вместо прямых вызовов Supabase.

Обоснование:
- Вариант 2 нарушает NFR-010 (минимум технологий, монолит вместо микросервисов) — Supabase
  self-hosted это отдельный стек из Kong, GoTrue, PostgREST, Realtime, Storage API, Studio —
  и отменяет три уже принятых и реализованных ADR (0004 Prisma, 0005 свои сессии, 0006 RLS)
  без причины лучше той, что была у их авторов.
- Вариант 3 не решает исходную проблему (два источника истины), а институционализирует её.
- Вариант 4 экономически бессмыслен: схема `fixly` менее зрелая (проверено при разборе —
  `invoices` без единого FK, `messages.task_id`/`votes.proposal_id` типа `text` против
  `uuid` PK, семь полей имени и четыре флага верификации в `profiles`, пять пересекающихся
  таблиц «единица работы»: `tasks`/`requests`/`orders`/`jobs`/`tenders`), не имеет тестов,
  не имеет спек/ADR, и не реализует отчёт по приказу №163 — ключевой аргумент продажи
  (CLAUDE.md). Взять её за канон значит выбросить готовую работу ради худшей модели.
- В проде Supabase нет живых пользователей, только тестовые учётки (подтверждено Рахимом
  2026-07-16) — перенос данных (ETL) не требуется, что резко снижает стоимость варианта 1.

### Практические следствия для реализации

- Flutter получает `ApiClient`, ходящий в те же `/api/**` роуты, что и сайт, авторизация —
  Bearer-токен поверх существующей таблицы `Session` (см. ADR-0012).
- Realtime (Supabase `.stream()`/`.channel()`, 29 мест в `fixly`) заменяется на SSE в монолите
  Next.js — не отдельный сервис (ADR-0012).
- Storage (`supabase.storage`, публичные `getPublicUrl()`) заменяется на существующий
  `/api/uploads` — файлы становятся приватными, не публичными по прямой ссылке.
- Схема Prisma расширяется срезами по мере переноса функций, которых в `fixlypwa` не было
  (звонки, AI-чат, YOLO-сканер, портфолио мастера) — не одной большой миграцией, т.к. переноса
  данных нет и торопиться некуда (SDD: спека → миграция для каждой функции отдельно).
- Проект Supabase (`wqxzraqzonyxnsrlysyt`) ставится на паузу после того, как `fixly` перестаёт
  на него ссылаться (последний шаг миграции).

## Последствия

- **Плюсы:** один источник истины, ADR-0003/0004/0005/0006 остаются в силе без ревизии;
  приложение наследует уже готовую RLS-изоляцию, отчёт по приказу №163, маркетплейс мастеров.
- **Минусы/компромиссы:** объём работы на стороне Flutter — 256 точек интеграции в 50 из
  68 dart-файлов подлежат переписыванию; часть функций `fixly` (звонки, AI, YOLO) временно
  остаются без бэкенда до соответствующих срезов (см. build-plan-3, фаза 8/срезы 28–32).
- **Что становится сложнее/невозможным:** Supabase Realtime/Storage/Auth как готовые
  примитивы недоступны — их функциональные аналоги (SSE, `/api/uploads`, Bearer-сессии)
  пишутся и поддерживаются в этом репозитории.
- **Влияние на другие ADR/требования:** не отменяет и не пересматривает ADR-0003/0004/0005/
  0006/0008/0009/0010 — только распространяет их на второго клиента. Детали мобильного
  клиента — ADR-0012. Полный план по срезам — `docs/build-plan-3-unification.md`.
