# ADR-0009: Маркетплейс заявок — кросс-тенантный доступ мастеров через витрину

Статус: предложен (2026-07-04). Связано: ADR-0006 (RLS-мультитенантность),
`docs/specs/marketplace.md` (спека фичи).

## Контекст

Продуктовая идея (заметки Рахима, 2026-07-04): внешние мастера (сантехники, электрики…)
видят заказы своего города, откликаются и выполняют работы. Референсы — YouDo, Uslugi.kz.

Продуктовые решения (зафиксированы Рахимом):
1. **Публикует председатель** — заявка попадает мастерам только после явного действия
   председателя («Опубликовать мастерам»), не автоматически.
2. **Мастера только проверенные** — доступ к ленте заказов после одобрения (верификация).
3. **ПДн скрыты до принятия** — до подтверждения мастер видит дом/район, категорию,
   описание, фото; точная квартира и контакты жителя раскрываются только после того,
   как председатель принял отклик мастера.

Техническая проблема: заявки (`Request`) — tenant-таблица под RLS с изоляцией по `osiId`
(deny-by-default). «Мастер видит все заказы города» — принципиально кросс-тенантное чтение.

## Рассмотренные варианты

**A. BYPASSRLS для роли мастера** (читать Request напрямую через `app_superadmin`).
Отклонён: одна ошибка в where-условии = утечка заявок всех ОСИ города со всеми ПДн.
Роль BYPASSRLS зарезервирована для внутренних админ-путей, не для публичной аудитории.

**B. Ослабить RLS-политику Request** (добавить «published видно всем мастерам»).
Отклонён: усложняет ядро изоляции, политика Request перестаёт быть тривиальной
(«только своя ОСИ»), каждый следующий разработчик обязан помнить об исключении.

**C. Витрина-проекция (ВЫБРАН): отдельная таблица `MarketListing`.**
При публикации председателем создаётся ЯВНАЯ копия-проекция без ПДн:
город, категория, маскированный заголовок/описание, фото, район/адрес дома (без квартиры),
ссылка на исходный Request (osiId+requestId — для обратной связи, мастеру не отдаётся).
Своя RLS-политика: `status='PUBLISHED'` читается ролью мастера по городу.

## Решение (вариант C)

- `Request` и его RLS-политика **не меняются** — изоляция ядра нетронута.
- Публикация = осознанное действие председателя, создающее запись в витрине.
  Копирование полей (а не JOIN к Request) — гарантия, что в витрину попадает только
  то, что явно разрешено копировать (whitelist, не blacklist).
- ПДн-раскрытие после принятия отклика — отдельным эндпоинтом, который проверяет
  `MarketOffer.status = 'ACCEPTED'` и отдаёт контакт/квартиру из исходного Request
  через forTenant (сервер знает osiId листинга; мастер тенант-контекста не имеет).
- Мастер — НЕ участник ОСИ: `Role` не расширяем; отдельная сущность `Master`
  (identity-слой, вне RLS) со статусом верификации. Сессии — те же самописные
  (телефон+OTP), тип субъекта различается наличием Master-записи.
- Синхронизация статусов: закрытие/отзыв заявки председателем снимает листинг
  с витрины (обновление по requestId — сервисный код, не триггеры БД, для простоты).

### Механизм RLS витрины (уточнение после ревизии кода 2026-07-04)

На уровне БД отдельной «роли мастера» НЕТ — всё приложение ходит как `app_login`, а RLS
завязан на один контекст `app.current_osi_id` (устанавливает `forTenant`). Поэтому доступ
мастера реализуется НЕ ролью, а **вторым контекстом + двумя permissive-политиками** (в Postgres
несколько permissive-политик объединяются через OR):

- Новый враппер `forMaster(city, fn)` (по образцу `forTenant`) ставит `SET LOCAL
  app.current_master_city = <city>` внутри транзакции. Контексты не пересекаются: в запросе
  мастера установлен только `master_city`, у председателя — только `osi_id`.
- `MarketListing` (несёт И `osi_id`, И `city`) получает ДВЕ политики:
  1. `tenant_iso` (как у всех): `osi_id = current_setting('app.current_osi_id')` —
     путь председателя (создание/управление/снятие через forTenant).
  2. `market_read`: `status='PUBLISHED' AND city = current_setting('app.current_master_city')` —
     путь мастера (только чтение опубликованного своего города; INSERT/UPDATE мастеру не даём).
- `MarketOffer` аналогично: мастер видит/создаёт свои офферы (по `master_id` из сессии),
  председатель — офферы на листинги своей ОСИ (tenant-политика по `osi_id`).
- Раскрытие ПДн после ACCEPTED — не через RLS витрины, а отдельным серверным путём через
  `forTenant` (сервер знает osiId листинга) с проверкой `MarketOffer.status='ACCEPTED'`.

## Последствия

+ Ядро мультитенантности не трогаем; поверхность утечки — только явный whitelist витрины.
+ Витрина масштабируется независимо (индексы по city/category/status).
− Дублирование данных (описание/фото копируются) — цена приватности; рассинхрон
  ограничен сервисным слоем публикации.
− Появляется понятие «город» — обязательное структурированное поле у Building и Master
  (сейчас адрес — свободный текст; миграция добавляет `city`).
