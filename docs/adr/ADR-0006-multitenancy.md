# ADR-0006: Модель мультитенантности (изоляция данных ОСИ)

- **Статус:** Accepted
- **Дата:** 2026-07-01
- **Контекст решения:** REQ-002, NFR-052, domain-model.md §3

## Контекст и проблема
Данные разных ОСИ должны быть строго изолированы. Способ изоляции определяет структуру БД,
запросы, безопасность и совместимость с Prisma (ADR-0004). Это фундаментальное решение —
поменять позже дорого.

## Рассматриваемые альтернативы
1. **Shared DB + `osiId` (discriminator column)** — все тенанты в одних таблицах, фильтр по osiId в каждом запросе.
2. **Shared DB + Postgres RLS (Row-Level Security)** — изоляция на уровне БД, политики по osiId.
3. **Schema-per-tenant** — отдельная схема Postgres на каждую ОСИ.
4. **Database-per-tenant** — отдельная БД на ОСИ.

## Сравнение (за / против)
| Критерий | osiId column | RLS | Schema/tenant | DB/tenant |
|---|---|---|---|---|
| Простота (1 разработчик) | высокая | средняя | средняя-низкая | низкая |
| Совместимость с Prisma | отличная | ограниченная (нужен raw/middleware) | ограниченная | сложно |
| Сила изоляции | зависит от кода | высокая (в БД) | высокая | максимум |
| Риск утечки между тенантами | выше (забыл фильтр) | ниже | низкий | минимальный |
| Масштаб/эксплуатация | просто | просто | сложнее (миграции ×N) | сложно |
| Стоимость на тенанта | минимальная | минимальная | средняя | высокая |

## Решение
**Shared DB + Postgres RLS.** Все тенанты в общих таблицах, но изоляция гарантируется на
уровне БД через Row-Level Security политики по `osiId`, а не только фильтрами в коде.
Обоснование: риск «забытого фильтра» в коде (osiId column) при росте кодовой базы неприемлем
для домена с финансовыми данными (начисления, платежи) — цена утечки между ОСИ высокая.

Единица тенанта — **Osi** (не Building): один RLS-контекст на ОСИ, что согласуется с Q-005
(1 ОСИ управляет N домами).

### Практические следствия для реализации
- Каждая тенантная таблица содержит `osiId` (FK на `Osi`).
- RLS-политика вида `USING (osi_id = current_setting('app.current_osi_id')::uuid)` на каждой
  тенантной таблице.
- Приложение обязано устанавливать `app.current_osi_id` в начале каждой транзакции/запроса
  (напр. через Prisma `$transaction` + `SET LOCAL` или middleware).
- Prisma не поддерживает RLS нативно — доступ к тенантным таблицам оборачивается в helper/
  middleware, гарантирующий установку контекста перед любым запросом. Это создаёт дисциплину,
  но не полагается только на неё — при отсутствии контекста RLS блокирует доступ по умолчанию
  (`DENY BY DEFAULT`), а не молча возвращает все строки.
- SuperAdmin-операции (кросс-тенантные) — отдельная роль БД/bypass RLS, используется только
  в явно помеченных административных путях.

> ⚠️ ДОПУЩЕНИЕ: конкретный механизм установки `app.current_osi_id` в Next.js/Prisma
> (SET LOCAL в транзакции vs connection-level) требует прототипирования при реализации —
> это техническая деталь, не блокирующая дизайн схемы.

### ✅ Результат спайка (2026-07-01) — риски сняты

Прототип `spikes/rls-prisma/` (Postgres 16 + PgBouncer transaction pooling + Prisma) —
**все 9 проверок пройдены**. Механизм подтверждён end-to-end через PgBouncer. Итоговые
решения для `schema.prisma`:
- Таблицы идентичности (`osi`, `users`, `sessions`, `user_osi_role`) — **вне RLS** (снимает
  bootstrapping-проблему, риск №1).
- Tenant-таблицы: `ENABLE` + `FORCE ROW LEVEL SECURITY`; политика `USING` + `WITH CHECK` по
  `osi_id = nullif(current_setting('app.current_osi_id', true), '')::uuid`. Без контекста →
  0 строк (DENY BY DEFAULT), не «все».
- Приложение подключается **обычной ролью** (не суперпользователь, не владелец, без `BYPASSRLS`).
- Обёртка `forTenant(osiId, fn)`: `prisma.$transaction` + `set_config('app.current_osi_id', …,
  is_local=true)` (== `SET LOCAL`, риск №2).
- PgBouncer в режиме `transaction` + `?pgbouncer=true` в URL — контекст не протекает между
  клиентами, сбрасывается на COMMIT (риск №3 снят).
- `WITH CHECK` блокирует запись строки в чужой тенант.
Детали и как перезапустить — `spikes/rls-prisma/README.md`.

### Ревизия: три конкретных технических риска (уточнено, найдены при разборе перед schema.prisma)

Ниже — не смена решения, а конкретизация «требует прототипирования» выше. Рекомендуется
короткий спайк (RLS + Prisma + PgBouncer на 2–3 таблицах) **до** написания полной
`schema.prisma`, т.к. ошибка здесь дорого стоит переписать.

1. **Bootstrapping-проблема.** Чтобы установить `app.current_osi_id`, приложение должно
   сначала прочитать сессию → пользователя → его связи `UserOsiRole`, чтобы узнать, какие
   `osiId` вообще доступны. Но если таблицы `User`/`Session`/`UserOsiRole` сами защищены той
   же RLS-политикой по `osiId`, получается замкнутый круг («курица и яйцо»): нет osiId, пока
   не прочитан User, а User не прочитать без osiId. **Решение:** эти три таблицы должны быть
   **вне тенантных RLS-политик** (либо читаются через отдельную bypass-роль БД, аналогично
   SuperAdmin-пути) — RLS применяется только к финансовым/доменным таблицам (Building, Account,
   Charge, Payment, Report и т.д.), не к таблицам идентификации.
2. **`SET LOCAL` требует явной транзакции на каждый запрос.** Обычный `prisma.model.findMany()`
   не даёт гарантии, что `SET LOCAL app.current_osi_id` и последующий SELECT выполнятся в одном
   и том же соединении с БД. На практике это означает: каждый доступ к тенантной таблице должен
   идти через Prisma `$transaction` (или Client Extension, оборачивающий вызовы) — это
   осознанный компромисс (дополнительный round-trip), а не побочный эффект, который можно
   упустить при реализации helper-обёртки.
3. **Несовместимость с PgBouncer connection-level `SET`.** NFR-020 предполагает PgBouncer в
   будущем для горизонтального масштабирования. В **transaction pooling mode** (стандартный
   режим для такого сценария) `SET LOCAL` внутри транзакции работает корректно, но
   connection-level `SET app.current_osi_id` — **нет** (соединение переиспользуется между
   разными клиентами/тенантами между транзакциями). Значит вариант «установить контекст на
   уровне соединения один раз» изначально исключён — обёртка должна использовать `SET LOCAL`
   внутри транзакции с самого начала, чтобы не переписывать это при введении PgBouncer позже.

## Последствия
- **Плюсы:** изоляция гарантирована БД, а не дисциплиной кода — соответствует NFR-052 и
  финансовому характеру данных; утечка между ОСИ становится architecturally сложной, а не
  просто «маловероятной».
- **Минусы/компромиссы:** больше первоначальной настройки (миграции с RLS-политиками,
  обёртка над Prisma-клиентом); каждый новый запрос к тенантным таблицам должен проходить
  через эту обёртку — требует дисциплины на уровне ревью кода.
- **Что сложнее:** админ-инструменты и аналитика, требующие кросс-тенантных запросов, нужно
  явно проектировать в обход RLS (осознанно, не случайно).
- **Влияние:** REQ-002, NFR-052 закрыты этим решением. schema.prisma пишется с `osiId` на
  каждой тенантной таблице + отдельным SQL-слоем миграций для RLS-политик (Prisma
  `migrate` + raw SQL в той же миграции).
