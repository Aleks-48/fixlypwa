# ADR-0012: Мобильный клиент — авторизация, реалтайм, файлы, push

- **Статус:** Accepted
- **Дата:** 2026-07-16
- **Контекст решения:** ADR-0011, `docs/build-plan-3-unification.md` §12а (срезы 19–20, 24)

## Контекст и проблема

ADR-0011 решает, ЧТО происходит (Flutter переезжает на API `fixlypwa`). Этот ADR решает КАК —
четыре независимых, но связанных технических вопроса, каждый из которых Supabase закрывал
бесплатно, а теперь их нужно закрыть в своём стеке:

1. Как нативный клиент передаёт сессию (сейчас — только httpOnly cookie, `src/lib/auth/
   session.ts`), если у Flutter нет автоматического cookie jar браузера?
2. Чем заменить Supabase Realtime (29 мест в `fixly`: чаты, объявления, голосования,
   звонки), если в `fixlypwa` реалтайма нет вообще?
3. Чем заменить `supabase.storage` (публичные `getPublicUrl()`), если в `fixlypwa` уже есть
   приватный `/api/uploads`?
4. Чем заменить Supabase Auth (Google/Apple Sign-In), если в `fixlypwa` есть только
   телефон+OTP и email+пароль/код (ADR-0005)?
5. Чем заменить `user_tokens`/`profiles.fcm_token` (Firebase Cloud Messaging), если в
   `fixlypwa` есть только Web Push/VAPID (`PushSubscription`)?

## Рассматриваемые альтернативы и решения

### 1. Транспорт сессии

**Альтернативы:** (A) `Authorization: Bearer <token>` поверх существующей таблицы `Session`;
(B) отдельная система токенов для мобильного (JWT, refresh-токены); (C) cookie jar в Flutter
(`dio_cookie_manager` + `cookie_jar`) — эмулировать поведение браузера.

**Решение: A.** `Session.id = sha256(token)` уже устроена как непрозрачный токен
(`src/lib/auth/crypto.ts`), не завязана на cookie — cookie лишь один из способов его
передать. `getCurrentAuth()` (`src/lib/auth/session.ts:55`) читает токен из `cookies()`;
меняется только это чтение — добавляется fallback на заголовок `Authorization: Bearer`,
остальная модель (TTL, `activeOsiId`, инвалидация) не меняется. Вариант B — не нужен,
удвоение систем авторизации без причины (NFR-010). Вариант C — хрупок и избыточен: смысл
Bearer в том, что клиенту не нужно эмулировать браузер.

### 2. Реалтайм

**Альтернативы:** (A) Server-Sent Events (SSE) в существующих Next.js route handlers;
(B) WebSocket-сервер; (C) поллинг с коротким интервалом; (D) отдельный realtime-сервис
(напр. Centrifugo, Ably).

**Решение: A с фолбэком на C для звонков.** SSE укладывается в монолит (`runtime = "nodejs"`
route handler, долгоживущий HTTP-ответ) без нового сервиса — соответствует NFR-010 и уже
принятой архитектуре (ADR-0002). Для чатов заявок, объявлений, голосований, уведомлений
задержка в секунды не критична — SSE достаточно. WebSocket (B) и отдельный сервис (D)
добавляют инфраструктуру ради симметричного канала, который здесь не нужен (клиент не шлёт
события обратно тем же каналом — он делает обычный POST). Поллинг (C) — временное решение
среза 21–22, пока SSE не реализован (срез 24), не финальная архитектура.

**Открыт по звонкам:** Jitsi-сигналинг (`calls`, `incoming_call_screen.dart`) требует
низкой задержки уведомления о входящем звонке. SSE может не подойти — решение откладывается
до спайка перед срезом 29 (build-plan-3 §12а), в этом ADR не фиксируется.

### 3. Файлы

**Альтернатива A (выбрана):** существующий `/api/uploads` (`src/app/api/uploads/route.ts`) +
файловый том в `docker-compose.yml`. **Загрузка** — только через авторизованный роут (вход
обязателен, MIME-контроль, пересжатие с зачисткой EXIF/GPS). **Отдача** — честно: файлы лежат
в `public/uploads` и отдаются Next статикой БЕЗ проверки прав; защита чтения — только
непредсказуемость имени (UUIDv4, ~122 бита энтропии), ссылки живут внутри tenant-данных под
RLS и наружу не публикуются. Это осознанно принятая на MVP obscurity-модель (уточнено по
code review 2026-07-16 — предыдущая редакция этого раздела ошибочно заявляла авторизованную
отдачу), практически эквивалентная Supabase `getPublicUrl()` по механике чтения, но с двумя
отличиями: наша загрузка авторизована и зачищает EXIF, и файлы физически в РК (ADR-0003).
**Альтернатива B (отклонена):** отдача через авторизованный route handler с проверкой членства
в ОСИ. Правильнее, но дороже (каждая картинка — запрос с сессией и RLS-проверкой вместо статики
Nginx/Next) — отложено как отдельный срез после ядра, вместе с решением Q-054 (S3 в РК).
Закрывает Q-060 из build-plan-3 в редакции «загрузка приватная, чтение по непубликуемой
UUID-ссылке»; полная приватная отдача — за Q-054.

### 4. Google/Apple Sign-In

**Альтернатива A (выбрана на срезы 18–27):** убрать из мобильного клиента на время миграции
ядра, вход — как на сайте (email-код/пароль, ADR-0005 ревизия 2026-07-15).
**Альтернатива B (отложена):** реализовать OAuth-провайдеры в своём бэкенде (Google — 1
провайдер, но App Store требует Sign in with Apple в комплекте с любым другим соц-логином —
то есть фактически 2 провайдера, не 1).

Решение: A. OAuth в своём бэкенде — заметный объём (redirect-флоу, верификация id_token,
привязка внешнего идентификатора к `User`) без спеки и без подтверждённого спроса от
пользователей (тестовые учётки, полевая валидация ещё не проведена — см. `needs.md`).
Не блокирует ядро миграции. Решение B рассматривается отдельным срезом после 27, если
полевая валидация с председателями/жителями покажет спрос на соц-вход. Закрывает Q-059.

### 5. Push-уведомления

**Решение:** два параллельных механизма, не один — это разные протоколы, которые нельзя
свести в общую таблицу. `PushSubscription` (Web Push/VAPID) остаётся для сайта как есть.
Добавляется identity-таблица `FcmToken` (по образцу `PushSubscription` — вне RLS, привязана
к `User`) для нативного клиента через `firebase-admin`. `Notification` остаётся единой
точкой создания уведомления (`notify()`, срез 7); доставка ветвится на оба канала, каждый
graceful-off без настроенных ключей — тот же паттерн, что уже принят для VAPID.

## Последствия

- **Плюсы:** ни один вопрос не требует новой инфраструктуры за пределами Next.js-монолита
  (кроме `firebase-admin` — уже необходим для FCM независимо от архитектурных решений здесь);
  авторизация остаётся одной системой на два клиента.
- **Минусы/компромиссы:** SSE на чатах/объявлениях — не такая же гарантия доставки, как
  Supabase Realtime «из коробки»; переподключение и backlog при обрыве соединения — на
  ответственности реализации (срез 24), не решены этим ADR.
- **Что становится сложнее/невозможным:** соц-вход недоступен до отдельного среза после 27
  (Q-059); публичные ссылки на файлы недоступны в принципе — не временное ограничение,
  а осознанный отказ (пункт 3 выше).
- **Влияние на другие ADR/требования:** ADR-0005 (auth) не пересматривается, только
  дополняется транспортом; ADR-0006 (RLS) распространяется на файлы, которые раньше были
  вне её действия. Реализация — build-plan-3-unification.md, срезы 19 (Bearer), 20 (FCM),
  24 (SSE).
