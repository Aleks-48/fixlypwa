# ADR-0010: Онлайн-оплата — симулятор эквайринга внутри монолита, не отдельный сервис

- **Статус:** Accepted
- **Дата:** 2026-07-14
- **Контекст решения:** REQ-033..036, `payments-online.md`, REQ-030 (эквайринг вне MVP — не отменяется)
- **Ревизия 2026-07-14 (после code review):** атомарность списания по нескольким бакетам и
  сверка `expectedAmount` — см. «Решение» и «Гонка при двойном клике» ниже.

## Контекст и проблема

Черновик ТЗ на «модуль выставления и оплаты счетов» пришёл написанным под чужой стек
(Supabase Edge Function на Deno, таблицы `invoices`/`transactions`, клиент — Flutter). У нас
уже есть свой контур начислений: `Tariff` → `Charge` → `Payment`, RLS-мультитенантность на
self-hosted Postgres (ADR-0006), API — Next.js route handlers в монолите (ADR-0002). Supabase
исключён требованием data residency (ADR-0003) — Edge Function из ТЗ неприменима буквально.

Нужно решить: (а) где физически живёт код симулятора, (б) заводить ли новые таблицы
`invoices`/`transactions` параллельно с `Charge`/`Payment`, (в) как оплата ложится на
модель бакетов (REQ-024), а не на единый «счёт».

## Рассматриваемые альтернативы

1. **Supabase Edge Function**, как в ТЗ — отдельный Deno-рантайм, отдельная БД/RLS.
2. **Новые таблицы `invoices` + `transactions`** поверх текущей модели, эквайринг — отдельный
   route handler в нашем монолите, но с дублирующей моделью данных.
3. **Route handler в монолите + расширение существующих `Payment`/`Charge`** — без новых
   сущностей, оплата пишется через уже существующий `addPayment()`.

## Сравнение (за / против)

| Критерий | Supabase Edge Function | Новые invoices/transactions | Route handler + Payment (выбрано) |
|---|---|---|---|
| Простота (1 разработчик) | низкая — второй стек, второй деплой | средняя — дублирует Charge/Payment | высокая — переиспользует существующий сервис |
| Data residency | нарушает (managed-облако) | ок (наша БД) | ок (наша БД) |
| Совместимость с отчётом (REQ-040/041) | требует отдельного ETL в наш Postgres | два источника правды по платежам — отчёт должен знать про оба | один источник правды — отчёт не меняется |
| Риск разъезда с REQ-024 (раздельные бакеты) | высокий — своя схема статусов | высокий — `invoice.status` не знает про бакеты | нет — использует существующий `incomeToBucket`/`recomputeStatuses` |
| Стоимость поддержки | новая инфраструктура | новая таблица + миграция логики отчёта | +1 функция +1 колонка |

## Решение

**Route handler в монолите (`POST /api/payments/checkout`), без новых таблиц.** Симулятор —
обычная серверная функция `payOnlineDemo()` в `src/lib/finance/service.ts`. Единственное
изменение схемы — `Payment.gatewayRef` (аналог `payment_gateway_ref` из ТЗ, чисто
информационная метка для истории платежей жителя). Списание по всем бакетам с долгом идёт в
**одной** `forTenant`-транзакции (не циклом отдельных вызовов с отдельными транзакциями на
бакет) — если бакетов несколько, платёж атомарен: либо оплачены все, либо ни одного.

Оплата гасит **весь текущий долг жителя** (все бакеты сразу), а не один `invoice_id` — потому
что в нашей модели нет сущности «счёт», есть Σ начислений минус Σ платежей по бакету
(REQ-031). Сумма пересчитывается на сервере **дважды** — до имитационной задержки (быстрый
отказ на заведомо неудачный кейс: долг 0 или расхождение с `expectedAmount`, которую клиент
показывал жителю при открытии шторки) и ещё раз внутри финальной транзакции, непосредственно
перед списанием. Это одновременно: защита от манипуляции суммой с фронта, естественная
идемпотентность (REQ-034, повторный вызов при долге 0 — no-op) и защита от тихого списания
другой суммы, чем та, на которую жителю показали кнопку «Оплатить X ₸» (REQ-036).

Демо-параметры ТЗ (задержка ~1.5 c, 5% случайный отказ «недостаточно средств») перенесены как
есть — они не зависят от стека, это чисто UX-приём для реалистичности демонстрации.

Гонка при двойном клике (два параллельных запроса читают один и тот же долг > 0) сознательно
не устраняется явной блокировкой строк — обоснование в `payments-online.md` §4. Перечитывание
долга **после** задержки (а не до неё) сужает окно гонки до времени одной транзакции вместо
всей 1.5-секундной задержки. Это приемлемо для демо-функции без реальных денег; при переходе к
реальному эквайрингу это нужно будет пересмотреть отдельным ADR.

## Последствия

- **Плюсы:** ноль новых таблиц с дублирующим смыслом; отчёт (REQ-040/041) автоматически видит
  онлайн-оплаты — это обычные `Payment`; аудит (REQ-090) достаётся бесплатно через
  `addPayment()`; данные не покидают инфраструктуру РК ни на секунду.
- **Минусы/компромиссы:** оплата по одному начислению/бакету выборочно не поддерживается —
  осознанно отложено (`payments-online.md` §6); гонка при двойном клике не заблокирована на
  уровне БД (см. выше).
- **Что становится сложнее/невозможным:** нативный Flutter-клиент из исходного ТЗ — не
  применимо, у нас PWA; прямое использование примера кода Edge Function из ТЗ — не применимо,
  переписан под route handler.
- **Влияние на другие ADR/требования:** не меняет ADR-0002/0003/0006. REQ-030 (эквайринг вне
  MVP) остаётся в силе — это демо-симулятор, не интеграция с банком.
