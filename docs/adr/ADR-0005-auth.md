# ADR-0005: Выбор системы аутентификации (self-hosted)

- **Статус:** Accepted (пересмотрено 2026-07-01 — см. «Ревизия» ниже)
- **Дата:** 2026-07-01
- **Контекст решения:** REQ-001, REQ-003, NFR-051, user-roles.md

> ⚠️ **Ревизия (та же сессия):** на момент первой версии этого ADR предполагалось, что
> **Lucia Auth** — поддерживаемая библиотека с адаптером БД. Проверка актуальной документации
> показала: **Lucia v3 официально deprecated**, проект переведён в статус «learning resource» —
> авторы прямо рекомендуют не подключать пакет как зависимость, а реализовать сессии вручную по
> их гайду (нет адаптерной модели БД — она признана недостаточно гибкой для low-level библиотеки).
> Источник: официальный migration-гайд lucia-auth/lucia, раздел «Migrate from Lucia v3».
> Итоговое решение ниже (§«Решение») скорректировано с учётом этого, само направление
> (self-hosted, полный контроль над сессиями) не изменилось.

## Контекст и проблема
Нужна self-hosted авторизация без внешних сервисов (data residency), с ролями (SuperAdmin/
Chairman/Accountant?/Resident), мультитенантностью и удобным для жителей способом входа.
Способ входа жителя (email/телефон/иное) ещё не определён (Q-020) и влияет на выбор.

## Рассматриваемые альтернативы
1. **Auth.js (NextAuth) v5** — популярно в Next.js, много провайдеров, адаптер под Prisma.
2. **Самописные сессии по паттерну Lucia** — opaque session token + таблица `Session` в
   Prisma, без пакета-зависимости (сам проект Lucia больше не распространяется как библиотека,
   см. «Ревизия» выше) — полный контроль, код полностью в репозитории.
3. **better-auth** — более новая self-host-first библиотека с адаптером Prisma, активно
   поддерживается, есть плагин для телефон+OTP.
4. **Внешний IdP (Keycloak self-hosted)** — мощно, но тяжёлый для одного разработчика.

## Сравнение (за / против)
| Критерий | Auth.js v5 | Самописные сессии (паттерн Lucia) | better-auth | Keycloak |
|---|---|---|---|---|
| Self-host / data residency | ✅ | ✅ | ✅ | ✅ (отд. сервис) |
| Простота (1 разработчик) | высокая | средняя | средняя-высокая | низкая |
| Контроль над сессиями | средний | максимум | средний-высокий | высокий |
| Вход по телефону/OTP | через кастомный Credentials-провайдер | вручную (код целиком наш) | есть готовый OTP-плагин | есть |
| Поддерживаемость пакета (2026) | активно поддерживается | н/д (нет пакета, только наш код) | активно поддерживается | активно поддерживается |
| Мультитенант (osiId в сессии) | реализуемо | реализуемо напрямую | реализуемо | сложнее интегрировать |
| Доп. инфраструктура | нет | нет | нет | +сервис (против NFR-010) |

## Решение
**Самописные сессии по паттерну, который описывал Lucia** (opaque token, hash в БД, таблица
`Session` в schema.prisma) — без зависимости от пакета `lucia`, т.к. он снят с поддержки как
библиотека. Способ входа жителя закрыт (Q-020) — телефон + OTP (SMS).

Обоснование то же, что и в первой версии ADR: телефон+OTP — нестандартный для готовых решений
сценарий (Auth.js «из коробки» заточен под email/OAuth, телефон+OTP там всё равно реализуется
как кастомный Credentials-провайдер с ручной логикой). Раз кастомную OTP-логику писать в любом
случае, а «библиотеки Lucia» для этого больше не существует, разумный выбор — реализовать
сессии самостоятельно (это буквально то, что рекомендует сам проект Lucia в своём миграционном
гайде), не добавляя взамен новую внешнюю зависимость без необходимости.

**better-auth** — жизнеспособная альтернатива, если в процессе реализации самописный OTP-флоу
окажется дороже ожидаемого; стоит держать в уме как fallback, а не выбирать сразу, чтобы не
привязываться к чужой абстракции без явной необходимости (см. NFR-010).

Keycloak отклонён как избыточная инфраструктура (нарушает NFR-010, простоту стека).

### Практические следствия для реализации
- Собственный OTP-флоу: генерация кода, отправка через SMS-шлюз (внешний сервис, но не
  хранит данные — только транспорт кода; см. Q-022-подобные вопросы по выбору шлюза — новый
  открытый вопрос **Q-030**), проверка, создание сессии (наша реализация, таблица `Session`).
- **Rate limiting на OTP обязателен** (см. NFR-054, добавлено при ревизии): лимит запросов
  кода по номеру телефона и по IP, cooldown между отправками, ограниченное число попыток
  ввода кода, TTL кода. Без этого — риск SMS-pumping/toll fraud за счёт вашего SMS-баланса.
- Модель `User` в schema.prisma: `phone` (уникальный, обязателен для Resident), `email`
  (опционален — может понадобиться для Chairman/SuperAdmin), связь с `Session` (своя таблица,
  session token хранится в виде hash, не в открытом виде — по паттерну Lucia).
- Роли (SuperAdmin/Chairman/Accountant/Resident) хранятся как атрибут User или отдельная
  связка User↔Role↔Osi — уточняется при проектировании схемы (не блокирует ADR).
- Для Chairman/SuperAdmin вход может остаться email+пароль (иной профиль пользователя,
  UX-приоритет другой) — уточнить при реализации, не противоречит решению.

> ❓ Q-030 (новый): выбор SMS-шлюза для OTP (казахстанский провайдер, стоимость, интеграция).

### Ревизия 2026-07-15: email — главный канал OTP (спека `auth-email.md`)

Появился первый клиент, а SMS-шлюз требует юрлица и регистрации альфа-имени (отложено,
решение Рахима). Поэтому одноразовый код доставляется **и на email** — единая форма входа
«Телефон или email» (REQ-005/006), самостоятельная регистрация по коду (REQ-007).
До подключения SMS-шлюза email — единственный рабочий канал в проде; телефонный канал
сохраняется в коде (dev/console) и включается позже сменой провайдера в `sms.ts`.
Парольный вход председателя (email+пароль) СОХРАНЯЕТСЯ, включая парольные функции админки
(REQ-112: временный пароль, сброс). `OtpChallenge.phone` обобщён до `identifier` + `channel`;
`User.phone` стал опциональным (email-only аккаунты). Транспорт писем — `src/lib/email.ts`
(console|smtp, nodemailer); письмо содержит только код (data residency, NFR-001).

## Последствия
- **Плюсы:** полный контроль над кастомным OTP-флоу без борьбы с чужими абстракциями;
  минимум зависимостей; согласуется с NFR-010 (простота); нет риска, что used-пакет снова
  окажется deprecated — код целиком в репозитории.
- **Минусы/компромиссы:** OTP/SMS-логику, включая security-детали (hashing токенов, rate
  limiting, тайминг-атаки при сверке кода), пишем и поддерживаем сами, без готового рецепта
  от поддерживаемого пакета; нужен внешний SMS-шлюз (не хранит данные, но это внешняя
  зависимость в критичном пути входа).
- **Что сложнее:** нет плагинной архитектуры провайдеров — расширение (например, добавление
  OAuth для Chairman в будущем) пишется вручную.
- **Влияние:** REQ-001 закрыт. Модель `User`/`Session` в schema.prisma проектируется с
  телефоном как первичным идентификатором для Resident. Связано с ADR-0006 (osiId в
  сессии/контексте для установки RLS-контекста при каждом запросе) — важно: таблицы
  `User`/`Session`/`UserOsiRole` должны быть вне тенантных RLS-политик (см. ревизию ADR-0006),
  иначе возникает bootstrapping-проблема при чтении сессии до того, как osiId известен.
