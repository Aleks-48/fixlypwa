# ADR-0008: Админка платформы — модель доступа суперадмина без BYPASSRLS в веб-рантайме

Статус: принят (2026-07-07). Связано: ADR-0005 (auth), ADR-0006 (RLS-мультитенантность),
ADR-0009 (маркетплейс — прецедент отказа от BYPASSRLS), `docs/specs/admin-panel.md` (спека),
`docs/build-plan-2-notifications-ui-admin.md` (план среза 9), Q-053 (одобрение мастеров).

## Контекст

Нужна админка платформы (срез 9): верификация мастеров маркетплейса (Q-053 — сейчас CLI),
управление подписками домов (REQ-070/071), провижининг аккаунтов председателей после продажи
(дополнение к self-service Q-051), статистика платформы. Аудитория — только мы (владелец
платформы), десктоп.

Два решения, которые надо зафиксировать:

1. **Кто суперадмин** — как техническая роль «владелец платформы» выражается в модели данных.
2. **Как админка читает/пишет данные** — тенантные таблицы закрыты RLS (deny-by-default),
   а админке нужен кросс-тенантный обзор.

## Решение 1: признак суперадмина — флаг `User.isSuperadmin`

**Выбрано:** булев флаг на identity-таблице `users` (`is_superadmin`, default `false`).
Гейт `/admin` и `/api/admin/**` проверяет только его.

**Рассмотрено и отклонено — роль `SUPERADMIN` в `UserOsiRole`** (вариант из build-plan-2):

- `UserOsiRole` — per-OSI членство; глобальная роль «владелец платформы» (user-roles.md §1:
  scope «глобальный») в ней не выражается без фиктивной привязки к какой-то ОСИ.
- Запись `UserOsiRole(SUPERADMIN, osiX)` уже сегодня даёт права председателя в osiX через
  `hasRole(..., "CHAIRMAN", "SUPERADMIN")` — гейт админки получал бы неожиданный побочный
  эффект (доступ к конкретному тенанту как управляющий).
- Enum-значение `Role.SUPERADMIN` **сохраняем** с этой узкой семантикой: точечный
  саппорт-доступ к конкретной ОСИ (по согласию клиента), НЕ признак админки.

**Назначение флага — только CLI** `scripts/make-superadmin.ts` (по образцу
`approve-master.ts`, подключение `DIRECT_URL` в обход приложения). Из веб-приложения поле
не мутируется нигде — нет API, который мог бы его выставить, значит нет пути эскалации
привилегий из веба. Вход суперадмина — обычные механизмы ADR-0005 (email+пароль или
телефон+OTP), отдельного логина нет.

## Решение 2: доступ к данным — БЕЗ BYPASSRLS в веб-рантайме

**Выбрано:** админка работает через уже существующие санкционированные пути:

- **Identity-таблицы вне RLS** (`Osi`, `User`, `UserOsiRole`, `Master`, `AdminAuditLog`) —
  обычный `prisma` (роль `app_login`). Этого хватает для: списка ОСИ, верификации мастеров,
  аккаунтов/ролей председателей, платформенных счётчиков по identity.
- **Тенантные таблицы** (`Building`, `Subscription`, `Apartment`, …) — через штатный
  `forTenant(osiId)`, где `osiId` берётся из списка identity-таблицы `Osi` **после** гейта
  `isSuperadmin`. RLS-политики не меняются; авторизация «можно ходить в любой тенант» —
  прикладная (гейт), как и у председателя («можно ходить в свой тенант» — тоже прикладная
  проверка `activeChairmanOsi` перед `forTenant`).

**Рассмотрено и отклонено — `adminPrisma` на роли `app_superadmin` (BYPASSRLS)**
(вариант из build-plan-2, шаг 2):

- Постоянно живущий в Next.js-процессе клиент, для которого RLS не существует: одна ошибка
  импорта/where — кросс-тенантная утечка. Ровно по этой причине ADR-0009 отклонил BYPASSRLS
  для мастеров.
- Потребовал бы обвязку (второй пул соединений, env, ESLint-запрет импорта вне `lib/admin`,
  проверку «намеренным нарушением» из DoD) — вся эта стоимость исчезает, если клиента нет.
- Выигрыш только один: платформенные счётчики одним запросом вместо цикла по ОСИ. На
  целевом масштабе (Кокшетау, десятки ОСИ — Q-031) цикл `forTenant` дешёв; при сотнях ОСИ
  счётчики можно кэшировать или считать офлайн.

Роль `app_superadmin` (BYPASSRLS) в БД **остаётся** — для CLI-скриптов обслуживания и
будущих офлайн-задач (миграции данных, разбор инцидентов). Инвариант после этого ADR:
**в веб-рантайме единственная роль БД — `app_login`; BYPASSRLS-подключений нет.**

## Аудит действий админки — `AdminAuditLog` (identity, append-only)

Существующий `AuditLog` — финансовый журнал ОСИ: `osiId NOT NULL`, enum из финансовых
сущностей, под RLS. Действия админки в него не ложатся: у смены статуса мастера нет osiId
вообще. Заводим отдельную identity-таблицу `AdminAuditLog` (actorUserId, action, entityId,
diff, createdAt), append-only, пишется на **каждую** мутацию `/api/admin/**` (REQ-110).
Финансовый `AuditLog` не трогаем (ни enum, ни nullable osiId) — ядро споров о деньгах
остаётся простым.

## UI-контур

`/admin/**` — самостоятельный shell по образцу `/master` (НЕ `AppShell`/`AppSidebar` — те
типизированы под chairman|resident). Не вошедший → redirect `/login`; вошедший
не-суперадмин → `notFound()` (404, существование админки не подтверждаем; API-роуты —
`Errors.forbidden()`, как в остальных контекстах). Desktop-first. Опционально при деплое:
nginx `location /admin` c `allow/deny` по IP (README, не хардкод).

## Последствия

- (+) Ядро изоляции (RLS, forTenant) не трогается вообще; нет нового класса риска в вебе.
- (+) Верификация мастеров переезжает из CLI в UI → Q-053 закрывается
  (`approve-master.ts` остаётся аварийным fallback).
- (−) Кросс-тенантные агрегаты — O(N ОСИ) транзакций; приемлемо для целевого масштаба,
  пересмотреть при росте (кэш/материализация — отдельным решением).
- (−) Два журнала аудита (финансовый ОСИ / платформенный) — осознанное разделение
  ответственности.
