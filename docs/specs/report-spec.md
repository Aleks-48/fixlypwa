## 1. Главный вывод для архитектуры

Отчёт — это **не** выборка «начисления/платежи по квартирам». Это полный **финансовый отчёт
о движении средств ОСИ** (казначейский отчёт) за период: остатки на банковских счетах +
задолженность + все поступления + все расходы с контрагентами. Из четырёх блоков формы
**текущая доменная модель (Charge/Payment/Tariff) покрывает только часть блока «Поступления»**
(взносы жителей). Три из четырёх блоков требуют данных, которых в модели нет:

| Блок формы | Что нужно | Есть ли в domain-model.md сейчас |
|---|---|---|
| 1. Остатки на счетах (текущий + сберегательный) | Банковские счета ОСИ и их остатки | ❌ нет сущности банковского счёта |
| 2. Задолженность (3 вида) | Σ начислений − Σ платежей по статьям | ⚠️ частично (Charge/Payment), но не по всем видам (парковки/кладовки) |
| 3. Поступления (7 категорий) | Взносы жителей + аренда + целевые + иные | ⚠️ частично (только взносы жителей) |
| 4. Расходы (детальное дерево 7.1–7.6) | Реестр расходов с контрагентами (БИН, назначение) | ❌ нет сущности расхода вообще |

**Следствие:** для генерации ключевой фичи нужны новые сущности — `BankAccount`,
`Expense` (расход с контрагентом и категорией), расширенные типы поступлений. Это подтверждает
риск из первого ревью: проектировать schema.prisma только под биллинг жителей — значит
получить схему, из которой невозможно собрать обязательный отчёт.

## 2. Структура месячной формы (Форма 1)

Шапка: адрес МЖД, форма управления (ОСИ/ПТ), наименование и юр. адрес организации, период,
дата.

**Блок 1–2 — Остатки на счетах:**
1. Остаток на **текущем** счёте в банке 2-го уровня (управление/содержание)
2. Остаток на **сберегательном** счёте в банке 2-го уровня (накопления на кап. ремонт)

**Блок 3–5 — Задолженность (на дату):**
3. Задолженность по обязательным взносам собственников квартир/нежилых помещений на
   управление и содержание
4. Задолженность по взносам собственников парковочных мест, кладовок
5. Задолженность по взносам на накопления на капитальный ремонт

**Блок 6 — Всего поступлений, в т.ч.:**
- 6.1 Взносы на управление и содержание (квартиры/нежилые)
- 6.2 Взносы за парковочные места, кладовки
- 6.3 Взносы на накопление на кап. ремонт (сберегательный счёт)
- 6.4 Плата за сданное в аренду общее имущество
- 6.5 Целевые взносы (квартиры/нежилые), не предусмотренные сметой
- 6.6 Целевые взносы (парковки/кладовки)
- 6.7 Иные поступления (добровольные, частные инвестиции)

**Блок 7 — Всего расходов, в т.ч.:**
- 7.1 Расходы по управлению, в т.ч.:
  - 7.1.1 Оплата труда за бухучёт/отчётность
  - 7.1.2 Оплата труда за управление
  - 7.1.3 Обязательные платежи в бюджет (налоги, отчисления)
  - 7.1.4 Банковские услуги
  - 7.1.5 Оплата за РКО
  - 7.1.6 Расходы на содержание офиса
- 7.2 Расходы по содержанию общего имущества, в т.ч.:
  - 7.2.1 Оплата услуг субъектам сервисной деятельности (с приложением актов), с разбивкой по
    видам услуг: дератизация/дезинсекция; ТО систем отопления/водоснабжения/водоотведения;
    ТО электроснабжения; ТО газоснабжения; подготовка к осенне-зимнему периоду; санитарное
    состояние МОП; санитарное состояние придомовой территории; приборы учёта; лифты
    (опасные техустройства); противопожарные мероприятия; иные. **Каждая строка — с указанием
    контрагента** (наименование физ./юр. лица, в образце — БИН).
- 7.3 Текущий ремонт общего имущества (на основании дефектного акта)
- 7.4 Коммунальные услуги на содержание общего имущества
- 7.5 Хозяйственные расходы (инвентарь, оборудование)
- 7.6 Капитальный ремонт

Подписи: **Бухгалтер**, **Председатель ОСИ / субъект управления**, **Совет дома** (три
подписанта, с М.П.).

> ⚠️ Расходование денег со сберегательного счёта (кап. ремонт) — только по решению собрания
> (сноска в форме). Согласуется с решением о раздельном учёте кап.ремонта (Q-032, glossary.md).

## 2а. Приватность отчёта — что публично, что скрывается (Q-013, правовой баланс)

Форма (Приложение 3) публикуется жителям и в объект информатизации ЖКХ. Баланс между
прозрачностью (ст. 42 ЖО) и ПДн (Закон № 94-V):

**Раскрывается в публичном отчёте:**
- Номера квартир/нежилых помещений; полезная площадь и доля в кондоминиуме (база тарифа).
- Суммы начислений, задолженностей, оплат **по каждой квартире**.
- В расходной части — **наименования поставщиков-юрлиц** (БИН, ТОО/ИП) и суммы контрактов.

**Скрывается из публичного доступа (система обязана НЕ показывать):**
- **ИИН** собственников-физлиц.
- Телефоны, личные email.
- Банковские реквизиты (карты, личные счета физлиц-должников).
- ПДн штатных сотрудников ОСИ (ФИО сантехника/дворника) — заменяются общей статьёй расхода
  («ФОТ производственного персонала — N ₸»), а не поимённо.

→ Следствие для реализации: у отчёта **два представления** — внутреннее (председатель/бухгалтер
видят всё) и публичное (жители, с вырезанными ПДн). Модель отчёта и права доступа (user-roles.md)
должны это разделять с самого начала.

## 3. Что показывает реальный образец (eosi.kz, январь 2024)

- Каждая расходная строка в образце — это фактически **отдельная банковская транзакция** с
  контрагентом: «БИН …, ИП/ТОО/НАО …, назначение платежа …, сумма». Т.е. расходная часть
  отчёта формируется из **выписки по банковскому счёту** (в образце — Kaspi), а не вводится
  сводными цифрами. → см. §5 (следствие для MVP).
- Поступления жителей показаны сводно по категориям (6.1–6.7), не по каждой квартире.
- Присутствуют «переводы собственных средств» между своими счетами (не доход/расход, а
  внутреннее движение) — нужно уметь помечать транзакции как internal transfer, иначе задвоят
  поступления/расходы.

## 4. Годовая форма (Форма 2) — на будущее

Структурно та же, но: (а) две колонки **план/факт**; (б) обязательные платежи 7.1.3 разбиты
на пенсионный/социальный налог, соцотчисления, медстрахование; (в) текущий ремонт 7.3 и
кап.ремонт 7.6 разбиты по подпунктам (кровля, фасад, подвал, инж. системы). Вне MVP, но
модель расходов должна допускать эту детализацию (категория + подкатегория), чтобы годовой
отчёт не потребовал переделки схемы.

## 4а. Периоды отчёта: месяц / квартал / год (REQ-045, добавлено 2026-07-04)

`generateReport` принимает произвольный диапазон — форма и снимок данных одни и те же,
меняется только период агрегации:
- **REQ-045**: председатель выбирает тип периода (месяц / квартал / год) при генерации;
  система считает `periodFrom/periodTo` (UTC, включительно) и пишет `Report.type`
  (`MONTHLY` | `QUARTERLY` | `ANNUAL` — `QUARTERLY` добавлен в enum миграцией).
- Подпись периода в списках и просмотре: «июль 2026» / «II квартал 2026» / «2026 год»
  (общий хелпер `reportPeriodLabel`).
- Годовая форма №2 с план/факт (см. §4) — ОТДЕЛЬНАЯ задача, вне REQ-045: годовой период
  пока рендерится той же месячной формой (агрегаты за год).

## 5. Следствие для MVP-скоупа (требует продуктового решения — Q-035)

Ценностное предложение (vision.md §3) — «отчёт одним нажатием, экономия часов». Но ~60% формы
это **расходы**, а расходы = банковские транзакции с контрагентами. Отсюда развилка:

- **Полный отчёт** = нужен реестр расходов, наполняемый импортом банковской выписки (Q-012) —
  только тогда «одно нажатие» реально экономит часы. F-3 (ручной ввод) покрывает поступления
  жителей, но не расходную часть.
- **Отчёт только по поступлениям** = MVP собирает блоки 1–3, 6 (взносы), а расходы (блок 7)
  председатель по-прежнему заполняет вручную → экономия времени частичная, ключевой «крючок»
  ослаблен.

Это первое реальное продуктовое решение по объёму MVP ключевой фичи — вынесено как **Q-035**.
