### 1а. ФИО аккаунта (REQ-146)

- **REQ-146 [MUST]** — `User.fullName` (identity, nullable) — ФИО, введённое на форме
  регистрации. Отдельно от `Occupant.fullName` (что видит председатель в реестре жителей —
  задаёт он сам при добавлении, может отличаться) и `Master.fullName` (анкета мастера) —
  оба контекстные/тенантные, `User.fullName` — только профиль аккаунта и предзаполнение форм.
- **REQ-147 [MUST]** — `POST /api/auth/otp/verify` принимает опциональный `fullName` —
  применяется ТОЛЬКО если передан (обычный вход поле не шлёт, существующее имя не
  перезаписывается пустым). `PATCH /api/auth/profile` — редактирование ФИО после
  регистрации, доступно и role-less пользователю (ждущему привязки).

## 1. Единая схема входа и регистрации (REQ-137)

Одна схема на оба клиента. Отдельной «регистрации» не существует — **первый вход по коду
создаёт аккаунт** (auth-email.md §3, уже реализовано на сайте и в приложении):

```
        ┌─ есть роль CHAIRMAN ──→ кабинет председателя
вход по коду (email/телефон)
        ├─ есть роль RESIDENT ──→ кабинет жителя
        │
        └─ ролей нет ──→ развилка новичка:
              ├─ «Я председатель» → форма «Создать ОСИ» (name, БИН?, адрес)
              │        → POST /api/osi (Q-051: создатель = CHAIRMAN) → онбординг дома
              └─ «Я житель» → экран «Сообщите председателю ваш email/телефон —
                       он привяжет вас к квартире» (роль появится после привязки, REQ-013)
```

- **REQ-137 [MUST]** — Развилка новичка одинакова на сайте и в приложении: пользователь без
  ролей видит ДВА пути (создать ОСИ / ждать привязки), а не тупик. Сайт: уже так (`/app`
  форма «Создать ОСИ» + блок «Как подключиться»). Приложение: сейчас тупик «не привязаны
  к дому» — добавляется кнопка «Я председатель — создать ОСИ» и форма (те же поля, что
  сайт; POST /api/osi + POST /api/buildings).
- **REQ-138 [MUST]** — Порядок «сначала председатель, потом жители» обеспечивается моделью,
  не UI-ограничением: житель без привязки не имеет роли и не видит данных (RLS); привязку
  выполняет председатель (addResident по телефону/email — upsert подхватывает уже
  зарегистрировавшегося жителя, REQ-013). Регистрироваться жители могут в любой момент,
  в кабинет попадают после привязки.
- **REQ-139 [SHOULD]** — Пароль остаётся доп. способом входа председателя НА САЙТЕ
  (решение 2026-07-15); в приложении — только код. Это не нарушение «одной схемы»: схема
  одна (код), пароль — дополнительная опция одного из клиентов.
- Приглашение жителей кодом дома / QR (жители сами выбирают квартиру, председатель
  подтверждает) — улучшение онбординга, НЕ входит в текущий объём → **Q-062**.

## 3. Интерфейс председателя в приложении (REQ-143, ревизия REQ-121)

- **REQ-143 [MUST]** — Роль CHAIRMAN в приложении получает свой шелл (таб-бар: Главная /
  Заявки / Объявления / Ещё) вместо экрана «используйте сайт». Работает сразу (роуты
  готовы или добавляются в R1): список заявок дома + смена статуса, создание объявления,
  уведомления, инфо. Остальное — каталог §2 с пометками 🔜/🌐.
- **REQ-144 [MUST]** — GET /api/requests получает параметр `?scope=building` (только для
  CHAIRMAN/SUPERADMIN активной ОСИ): заявки всех жителей дома. Дефолт (без параметра) —
  как сейчас, только свои (REQ-безопасность: житель чужие заявки не видит).
- **REQ-145 [SHOULD]** — Полный функционал управления (финансы, отчёты, реестр, импорт)
  остаётся на сайте (desktop-first, Excel-подобные задачи), приложение председателя —
  оперативные задачи (заявки, объявления, уведомления). Ревизия REQ-121: формула
  «председатель = только сайт» → «председателю доступны оперативные функции в приложении,
  управление — на сайте».

## 3а. Реализация R2 (2026-07-17) — что готово и известный пробел

R2 закрыт: `start_screen.dart`/`register_screen.dart` (роль → ФИО+контакт → код → шаг по
роли), `create_osi_screen.dart` (ОСИ→дом), `chairman_home_shell.dart` + `chairman_requests_
screen.dart` + `chairman_announcements_screen.dart` (REQ-143/144), `apartments_residents_
screen.dart` (REQ-137/138 §8 — постоянная функция, не разовый визард), `master_application_
screen.dart` (REQ-068).

⚠️ **Известный пробел (не блокирует DoD R2):** анкета мастера не даёт роли в `UserOsiRole`
(Master — отдельная identity-модель) — сервер `/api/auth/me` не возвращает статус анкеты,
поэтому `HomeRouter` не может отличить «мастер ждёт модерации» от «просто role-less» при
повторном входе. Мастер видит статус только сразу после отправки анкеты в том же сеансе;
закрыть — добавить `GET /api/master/me` + ветку в `HomeRouter`, предмет среза 25 (там же
появляется настоящий кабинет мастера) — заводить отдельный REQ сейчас преждевременно, само
решение зависит от формы кабинета мастера в 25.

## 3б. Реализация R3 (2026-07-17) — каталог функций и выравнивание сайта, трек R закрыт

Единый источник каталога — по одному файлу на клиента (не общий код между репозиториями,
REQ-142): `src/lib/featureCatalog.ts` (сайт) и `lib/core/feature_catalog.dart` (приложение).
Оба содержат ту же таблицу §2, но обновлённую под факт после R2 — три строки, отмеченные в
§2 как 🔜→✅ для председателя в приложении (создание ОСИ/дома, заявки+тред, объявления), стали
✅, а не 🔜 (R2 их уже реализовал); «Реестр квартир/жителей» для председателя в приложении —
тоже ✅, не 🌐 (`apartments_residents_screen.dart` — постоянная функция, не заглушка-ссылка на
сайт, как предполагалось в исходной таблице).

Приложение: `feature_catalog_list.dart` (`FeatureCatalogSection`) — общий виджет для «Ещё»
председателя и «Профиля» жителя, различие только флагом `isChairman`. ✅-пункты — статичные
строки (это уже свои вкладки/экраны, дублировать переход в каталоге незачем); 🔜/🌐-пункты
кликабельны → `feature_status_sheet.dart` показывает 1–2 фразы и срез (REQ-141) через
`showModalBottomSheet`, а не отдельный экран-заглушку — решение по месту (легче в реализации,
тот же эффект «не мёртвая кнопка»).

Сайт: лендинг (`src/app/page.tsx`) — две кнопки «Вход»/«Регистрация» вместо «Вход для
жителя»/«Вход для председателя» (решение §0). `CodeForm` (LoginForm.tsx) получила
`collectFullName` — поле ФИО показывается и отправляется в `otp/verify` ТОЛЬКО когда форму
рендерит `RegisterCodeForm`; `/login` использует ту же `CodeForm` без этого флага — поле не
появляется (проверено e2e-регрессией). Каталог на сайте показывает не весь список (REQ-140
всё равно требует видимость, но сайт и так ✅ почти everywhere) — свёрнутый `<details>` список
`FeatureCatalogSoonList` со статусом `soon`, той же визуальной свёрсткой, что уже был у пункта
«Настройки» (сайдбар lg+ и мобильное меню-шторка — один компонент на оба места).

Верификация: сайт — typecheck/lint чисто, unit 24, integration 52 (без изменений — R3 не
трогал бэкенд), e2e 21 (новый `register-form.spec.ts`, 4 теста: регрессия `/login` без ФИО,
регистрация жителя/председателя с ФИО через `page.evaluate(fetch(...))` — `page.request` НЕ
шарит httpOnly-cookie с браузерным контекстом, в отличие от Bearer-тестов в
`onboarding-unified.spec.ts`, — и видимость каталога в мобильном меню). Приложение: flutter
analyze 0 ошибок (377 — тот же withOpacity-паттерн, не новые проблемы), web-сборка (DDC, 1648
скриптов) грузится без ошибок консоли (Firebase/Supabase init прошли).

Трек R (R1+R2+R3) закрыт полностью.
