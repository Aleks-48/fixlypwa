# Domain Model — предметная область ОСИ

> Статус: DRAFT · Версия: 0.1 · Дата: 2026-07-01
> Общий язык проекта (ubiquitous language). Ложится в основу `/prisma/schema.prisma`.
> Термины определяются в `glossary.md`. Открытые вопросы дублируются в `open-questions.md`.

## 1. Обзор сущностей

Черновой список ключевых сущностей MVP. Точные атрибуты и типы уточняются при написании схемы.

| Сущность | Смысл | Ключевые связи |
|---|---|---|
| **Osi** (ОСИ) | Объединение собственников — единица тенанта | 1 ОСИ → N Домов (закрыто Q-005); владеет всеми данными тенанта |
| **Building** (Дом) | Многоквартирный дом под управлением ОСИ | принадлежит Osi; 1 → N Квартир |
| **Apartment** (Квартира) | Единица собственности в доме | принадлежит Building; связана с Лицевым счётом/жителями |
| **Account** (Лицевой счёт) | Учётная единица начислений по квартире | 1 Квартира = 1 Account (закрыто Q-006) |
| **Owner** (Собственник) | Физлицо, юридически владеющее квартирой | связан с Apartment (1 квартира может иметь неск. собственников — доли); закрыто Q-007 |
| **Occupant** (Проживающий/Житель) | Физлицо, фактически проживающее в квартире, пользователь кабинета | связан с Apartment; может совпадать или не совпадать с Owner; закрыто Q-007 |
| **User** (Пользователь) | Учётная запись входа в систему | связан с Owner/Occupant/Председателем через роль; идентификатор — телефон (закрыто Q-020, ADR-0005) |
| **Role** (Роль) | Права доступа | см. `user-roles.md` |
| **Tariff** (Тариф) | Ставка начисления по статье расходов (напр. тг/м² по эксплуатации, отдельно — целевой сбор, кап.ремонт) | принадлежит Osi/Building; закрыто Q-008 (несколько статей) |
| **Charge** (Начисление) | Начисленная к оплате сумма за период | привязано к Account + период + Tariff |
| **Payment** (Платёж) | Факт оплаты жителем (поступление) | привязан к Account; уменьшает задолженность |
| **BankAccount** (Банковский счёт) | Расчётный счёт ОСИ. Минимум два: **текущий** (управление/содержание) и **сберегательный** (накопления на кап.ремонт) | принадлежит Osi/Building; несёт остаток (строки 1–2 отчёта). Добавлено при разборе PDF-формы, см. report-spec.md |
| **Expense** (Расход) | Факт расхода ОСИ с контрагентом (блок 7 отчёта) | привязан к BankAccount/Building + период + категория расхода + контрагент. **Новая сущность — без неё отчёт не собрать.** См. report-spec.md |
| **Counterparty** (Контрагент) | Получатель платежа по расходу (ИП/ТОО/НАО, БИН, наименование) | связан с Expense; в реальном отчёте каждая расходная строка именует контрагента |
| **Report** (Отчёт) | Сформированный месячный отчёт по дому | привязан к Building + период; ключевая фича. Собирает: остатки BankAccount + задолженность (Charge−Payment) + поступления (Payment по категориям) + расходы (Expense по категориям) |
| **Subscription** (Подписка) | Коммерческая подписка на дом | привязана к Building (закрыто Q-009 — единица тарификации = дом, не Osi целиком) |

**Задолженность (Debt/Balance)** не отдельная сущность, а вычисляемое значение
= Σ Charge − Σ Payment по Account (закрыто Q-010).

> 🔴 **КРИТИЧНО (добавлено после разбора реальной формы отчёта, 2026-07-01):** обязательный
> месячный отчёт — это полный **финансовый отчёт о движении средств ОСИ**, а не выборка по
> квартирам. Из 4 блоков формы (остатки на счетах / задолженность / поступления / расходы)
> исходная модель Charge/Payment/Tariff покрывала только взносы жителей. Поэтому добавлены
> `BankAccount`, `Expense`, `Counterparty` и категоризация поступлений/расходов — **без них
> ключевую фичу (F-4) реализовать нельзя**. Полная структура формы и её юридический источник —
> в `report-spec.md`. Это прямо подтверждает риск, отмеченный в ревью: нельзя писать
> schema.prisma только под биллинг жителей.

> ⚠️ ДОПУЩЕНИЕ (уточнено при ревизии): формулировка выше верна только **в разрезе одной
> статьи** (эксплуатация / целевой сбор / кап.ремонт), не одним числом на Account целиком.
> Кап.ремонт — юридически обособленный накопительный фонд (см. glossary.md), переплата по
> нему не может закрывать долг по эксплуатации и наоборот. Значит `Payment` обязан нести
> статью (`tariffCategory`), и задолженность считается как Σ Charge − Σ Payment **по каждой
> статье отдельно**, суммарная цифра в UI — это сумма трёх независимых остатков, не единое
> вычитание.
>
> **Q-032 закрыт:** `tariffCategory` на `Payment` — **обязательное** поле, заполняется
> председателем вручную при вводе (REQ-024). Если реальный платёж жителя покрывает несколько
> статей разом, председатель вводит несколько строк `Payment` (по одной на статью) — никакой
> авто-распределяющей логики (FIFO и т.п.) в MVP нет, сознательно ради простоты и
> объяснимости жителю при споре о деньгах. Авто-распределение для импорта банковской выписки
> (REQ-032, вне MVP) отложено до Q-012.

## 2. Схема связей (черновик, текстом)

```
Osi (tenant root)
 ├── 1..N Building ── 1..1 Subscription (единица тарификации — дом, закрыто Q-009)
 │        └── 1..N Apartment
 │                 ├── 1..1 Account ──< Charge >── Tariff (по статьям: экспл./целевой/кап.рем.)
 │                 │        │      └──< Payment
 │                 ├──< Owner (собственник, юр. владение, возможны доли) ── User ── Role
 │                 └──< Occupant (проживающий, пользователь кабинета) ── User ── Role
 ├── 1..N Tariff (эксплуатация | целевой сбор | кап.ремонт — минимум 3 статьи)
 └── 1..N Report (per Building × период)

User ──< UserOsiRole >── Osi   (многие-ко-многим, закрыто Q-011: председатель может
                                 состоять в нескольких ОСИ; связующая таблица несёт роль)
```

**Q-005 закрыт:** ОСИ управляет N домами — верхний уровень тенанта — `Osi`, не `Building`.

## 3. Идентичность и мультитенантность

Все тенантные сущности несут `osiId` (tenant key). **ADR-0006 принят:** изоляция —
Shared DB + **Postgres RLS** по `osiId` (не только фильтр в коде). Единица тенанта — `Osi`.
Технические следствия (установка RLS-контекста на запрос, обёртка над Prisma) — см. ADR-0006.

**Q-011 закрыт:** `User` связан с `Osi` многие-ко-многим через связующую сущность
`UserOsiRole` (userId, osiId, role) — один председатель может состоять в нескольких ОСИ,
роль назначается на каждую связь отдельно. Активная Osi в сессии определяет RLS-контекст
(см. user-roles.md §3).

## 4. Жизненные циклы

- **Charge:** `открыто` → `частично оплачено` → `оплачено` (3 состояния оплаты, не 4).
  > ⚠️ ДОПУЩЕНИЕ (уточнено при ревизии): «просрочено» — **не** четвёртое значение того же
  > enum, а независимый вычисляемый признак (`dueDate` в прошлом И статус ≠ «оплачено»).
  > Начисление может быть одновременно «частично оплачено» и «просрочено» — эти два состояния
  > ортогональны, единый enum из 4 значений не способен это выразить корректно. Q-023 в этой
  > части пересмотрен: enum статуса оплаты — 3 значения, просрочка — computed-поле поверх него.
- **Payment:** зафиксирован вручную председателем (MVP, без эквайринга) → сопоставлен с Account.
  Способ ввода (ручной/импорт) — **Q-012 остаётся открытым**, нужен реальный образец у председателя.
- **Report:** черновик → сформирован → опубликован жителям. Формат вывода —
  **Q-013 остаётся открытым**, нужен реальный образец текущего Excel-отчёта.
- **Subscription:** trial → active → past_due → canceled. Привязана к Building (закрыто Q-009).

## 5. Атрибуты (заполнить при написании schema.prisma)

Для каждой сущности ниже — заглушка. Оставшиеся [TBD] не блокируют схему, уточняются по ходу.

- **Osi:** id, название, БИН/юр.реквизиты[TBD], адрес, дата регистрации, [TBD]
- **Building:** id, osiId, адрес, кол-во квартир, год постройки[TBD], [TBD]
- **Apartment:** id, buildingId, номер, площадь (м²), [TBD]
- **Account:** id, apartmentId (уникальный — 1:1), номер лицевого счёта, баланс(вычисл.), [TBD]
- **Owner:** id, apartmentId, ФИО, контакты, ИИН[TBD — ПДн, см. NFR-051], доля владения[TBD]
- **Occupant:** id, apartmentId, userId, ФИО, телефон (= идентификатор User), [TBD]
- **User:** id, phone (уникальный, первичный идентификатор для входа), email[опц., для Chairman], roleId
- **Session:** id, userId, tokenHash, expiresAt (своя таблица, session token хранится как hash — см. ADR-0005)
- **UserOsiRole:** userId, osiId, role (связующая таблица many-to-many User↔Osi)
- **Tariff:** id, osiId/buildingId, статья (enum: эксплуатация | целевой сбор | кап.ремонт), тип ставки (за м²/фикс), ставка, период действия
- **Charge:** id, accountId, tariffId, период (месяц), сумма, статус оплаты (enum 3 значения: открыто|частично_оплачено|оплачено), dueDate («просрочено» — computed из dueDate+статуса, см. §4)
- **Payment:** id, accountId, сумма, дата, способ, **tariffCategory** (статья, к которой отнесён платёж — обязательное поле, выбирается председателем вручную при вводе, см. §1, Q-032 закрыт), incomeCategory (категория поступления 6.1–6.7, см. report-spec.md)
- **BankAccount:** id, osiId/buildingId, тип (enum: текущий | сберегательный), наименование банка, номер счёта, текущий остаток (снимок на дату отчёта)
- **Expense:** id, buildingId, bankAccountId, дата, сумма, **expenseCategory** (enum по строкам 7.1.1–7.6, см. report-spec.md), counterpartyId, назначение (текст), isInternalTransfer (bool — «перевод собственных средств», не доход/расход), [ссылка на акт — для 7.2.1]
- **Counterparty:** id, osiId, наименование, БИН/ИИН[опц.], тип (ИП/ТОО/НАО/физлицо)
- **Report:** id, buildingId, период, содержимое/ссылка, статус, дата формирования, подписанты (бухгалтер/председатель/совет дома), [формат вывода — Q-013]
- **Subscription:** id, buildingId, план, статус, период, [TBD]
- **AuditLog** (добавлено при ревизии, см. NFR-055): id, osiId, entityType (Charge|Payment|Tariff),
  entityId, action (create|update|delete), diff/snapshot, actorUserId, createdAt. Append-only,
  без UPDATE/DELETE со стороны приложения. Обоснование — ключевая ценность продукта
  (vision.md §3) это прозрачность и снятие споров «куда ушли деньги»; без неизменяемого
  журнала правок начислений/платежей система не может подтвердить ни одну из сторон спора.

### Модуль коммуникации (Фаза 1, features.md блок B)
- **Announcement:** id, buildingId, authorUserId, заголовок, текст, scope (дом|подъезд|квартира),
  targetIds, isPinned, createdAt; читатели — через AnnouncementRead.
- **AnnouncementRead:** announcementId, userId, readAt (отметки о прочтении).
- **Request** (заявка жителя): id, buildingId, apartmentId, authorUserId, категория, текст, фото,
  статус (принята|в_работе|решена), createdAt; комментарии — через RequestMessage (тред).
- **InfoItem** (инфо-раздел дома): id, buildingId, тип (вывоз мусора|аварийные контакты|реквизиты|
  контакты председателя|прочее), заголовок, содержимое.

### Модуль голосований (Фаза 1 lite / Фаза 3 легитимные, features.md блок C)
- **Poll** (быстрый опрос): id, buildingId, вопрос, варианты, дедлайн, тип (lite|legitimate).
- **Vote:** id, pollId, userId, вариант, createdAt; для legitimate — доля голоса (по площади/доле
  владения) и признак верификации собственника (см. блок E, Q-039).
- **Meeting** (собрание, Фаза 3): id, buildingId, повестка, кворум-требование, статус, протокол/
  ссылка, подписи ЭЦП. Юридически значимое — требует верификации собственника и Digital ID.

> ⚠️ ДОПУЩЕНИЕ: `Owner` и `Occupant` — раздельные сущности (см. §1, закрыт Q-007), но обе
> опционально связаны с `User` (не у каждого Owner обязательно есть логин; у Occupant —
> обязателен, т.к. это основной пользователь кабинета).

> ⚠️ ДОПУЩЕНИЕ (Q-033 закрыт при ревизии): кабинет жителя (F-5, REQ-050/051/052) показывает
> данные **Account/Apartment**, к которой привязан текущий Occupant — включая случаи, когда
> Occupant не совпадает с Owner (например, наниматель). Это значит наниматель видит начисления
> и долг квартиры, собственником которой не является. Решение подтверждено: Occupant —
> фактический пользователь кабинета независимо от юридического владения; более гранулярная
> модель (скрывать историю/долг от нанимателя) сознательно не выбрана как избыточная
> сложность для MVP. Остаётся рабочим допущением, ожидающим продуктовой валидации на реальных
> председателях (см. критерии успеха vision.md §7), не юридический вопрос.

> ⚠️ ДОПУЩЕНИЕ (добавлено при ревизии): установка RLS-контекста (ADR-0006) требует прочитать
> `User`/`Session`/`UserOsiRole` **до** того, как `osiId` известен — эти три таблицы должны
> находиться вне тенантных RLS-политик (см. ревизию в ADR-0006), иначе возникает
> bootstrapping-проблема «курица и яйцо».
