# Спека: импорт данных из реальных выгрузок (образцы ОСИ «Центральный 2 / 2Б», Кокшетау)

> Статус: DRAFT (структуры зафиксированы, реализация не начата) · Дата: 2026-07-18
> Основание: Рахим передал 10 реальных документов от председателя ОСИ «Центральный 2/2Б»
> (2026-07-18) — Q-012 в части образцов ЗАКРЫТ для квартир/долгов/платежей терминалов.
> ⚠️ Сами файлы содержат ПДн (ФИО, ИИН, телефоны реальных жителей) и в репозиторий НЕ
> кладутся — здесь только структура. Оригиналы у Рахима.

## 0. Что это за файлы и откуда

Выгрузки из системы учёта, которой ОСИ пользуется сейчас (в реестре есть колонка «ЛС ЕРЦ»,
файл долгов назван `systemReports_debts_…` — вероятно, eOSI/Управдом-подобная система), плюс
реестры платежей от платёжного оператора (АПО, канал «Платёжные терминалы») и юридический
пакет ОСИ. **Ключевой вывод: три «услуги» системы-источника один-в-один совпадают с нашими
тремя бакетами `TariffCategory`** (ADR по REQ-024 подтверждён реальными данными):

| Услуга в выгрузках | Наш бакет |
|---|---|
| Текущие взносы на управление и содержание общего имущества | `MAINTENANCE` |
| Накопительные взносы на капитальный ремонт | `CAPITAL_REPAIR` |
| Целевой взнос | `TARGETED` |

## 1. Реестр помещений/квартир (`Помещенияквартиры_*.xlsx`)

Лист «Помещенияквартиры», ~73 помещения (дом 2Б). Шапка — строка 4, данные со строки 5:

`Номер | Собственник | Владелец | ИИН | Телефон | Тип | ЛС ОСИ | ЛС ЕРЦ | Этаж | Площадь | Полезная площадь | Проживает | Зарегистрировано`

- «Владелец» — значение из {Собственник, Арендатор} (роль контакта, не отдельное лицо).
- «Тип» — {Жилое, …} (нежилые помещения существуют в домене — см. §5 пробел «тип помещения»).
- Маппинг на нашу модель: `Apartment.number ← Номер`, `Apartment.area ← Площадь`,
  `Owner.fullName/iin/phone ← Собственник/ИИН/Телефон`, `Account.accountNumber ← ЛС ОСИ`
  (сейчас генерируем `A-<номер>` — при импорте сохранять реальный ЛС!), этаж — некуда (пробел).
- Качество данных: ФИО в произвольном регистре и полноте («ЮЛИЯ МАРЧЕНКО», «Герасимова »,
  с хвостовыми пробелами), ИИН/телефон заполнены НЕ у всех (~⅓ пусто), «Проживает/
  Зарегистрировано» — нули. Парсер обязан быть терпимым: трим, пустые → null, без валидации
  обязательности.

## 2. Оборотно-сальдовая ведомость (`Оборотно_сальдовая_ведомость_*.xlsx`)

5 листов. «Общая ведомость» (~248 строк): группировка «строка помещения → 3 строки услуг»:

`№ помещения | ФИО собственника | Лицевой счет | Владелец | Услуга | Сальдо на начало, тг. | Начислено за период, тг. | Корректировки, тг. | Оплачено за период, тг. | Пеня, тг. | Долг, тг.`

(числовые колонки идут через пустую ячейку — генератор делает merged-подобную вёрстку).

Полистовая разбивка по каждому бакету (3 листа с одинаковой шапкой):

`№ квартиры/помещения | Лицевой счет | Долг на начало, тг. | Начислено, тг. | Корректировки, тг. | Оплачено, тг. | Пеня, тг. | Долг на конец, тг.`

Лист «Должники»: `№ помещения | Лицевой счет | <3 бакета> | Всего`.

**Главная ценность — «Долг/Сальдо на начало»**: онбординг существующего ОСИ должен уметь
импортировать НАЧАЛЬНЫЕ сальдо по бакетам (дом живёт не с нуля). У нас такого понятия нет —
см. §5.

## 3. Отчёт по должникам (`systemReports_debts_*.xlsx`)

Лист «Должники» (шапка — строка 4): `№ помещения | Лицевой счет | Накопительные взносы на
капитальный ремонт | Текущие взносы на управление и содержание общего имущества | Целевой
взнос | Пеня | Всего`. Подтверждает бакеты + пеню.

## 4. Реестры платежей АПО (`APOCentral2b*.XLS`)

⚠️ Формат файла — НЕ бинарный XLS, а **SpreadsheetML (Excel 2003 XML)**, парсится как XML.
Два потока: `…overhaul…` (капремонт) и `…utilities…` (текущие взносы). Колонки:

`Дата операционного дня | Код платежа | Уникальный идентификатор | Лицевой счет | Сумма | Комиссия | ФИО | ИИН | Период | Адрес | Канал приема платежа`

- «Канал приёма платежа» = «Платёжные терминалы»; «Период» — текстом («ИЮЛЬ АВГУСТ
  СЕНТЯБРЬ» — оплата за 3 месяца одной суммой!); «Адрес» — конкатенация без разделителей
  («ЦЕНТРАЛЬНЫЙ2Б49» = мкр + дом + квартира); в образце «Лицевой счёт» заполнен ФИО (грязно).
- Это фактический формат импорта платежей (родственник Q-012-выписки Kaspi): маппинг
  `Payment.amount ← Сумма`, `paidAt ← Дата`, `gatewayRef ← Уникальный идентификатор`
  (идемпотентность повторного импорта!), лицевой счёт — матчить по квартире из «Адрес»
  с фолбэком на ЛС. Поток файла определяет `incomeCategory`.

## 5. Пробелы нашей модели, вскрытые образцами (Q-063)

| Пробел | Где всплывает | Что делать |
|---|---|---|
| **Пеня** | ОСВ, оба отчёта должников | Решить: MVP без пени (поле игнорируем при импорте) или модель `Charge`-подобной пени. НЕ начинать без решения Рахима |
| **Корректировки** | ОСВ | Это REQ-022 (SHOULD, не реализован). Импорт может свести их в начальное сальдо |
| **Начальные сальдо** | ОСВ «Долг на начало» | Нужен механизм opening balance при онбординге существующего дома (сейчас дом всегда «с нуля») |
| **Тип помещения (жилое/нежилое)** | Реестр квартир | `Apartment` без типа; отчёт №163 различает квартиры/нежилые (IncomeCategory уже различает). Поле `Apartment.type?` |
| **Реальный номер ЛС** | Везде | `Account.accountNumber` при импорте брать из «ЛС ОСИ», не генерировать `A-<номер>` |
| **Этаж** | Реестр квартир | Некритично; поле `Apartment.floor?` — по желанию |

## 6. Юридический пакет (docx, для Тир 2 и библиотеки документов — срез 32)

- **Устав ОСИ** (рус + каз, типовой) — «Центральный 2», редакция по протоколу №1 от 01.04.2025.
- **Протокол собрания** — образец: собрание ПИСЬМЕННЫМ порядком (89 собственников, кворум 63).
- **Лист голосования** (явочный порядок) и **Лист регистрации** — таблицы ФИО/№ кв./подпись.
Ценность: реальные шаблоны для будущего генератора документов (срез 32) и референс структуры
голосований Тир 2 (письменный vs явочный порядок — оба существуют на практике).
