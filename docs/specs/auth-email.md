# Спека: Единый вход и регистрация по email-коду

> Статус: ACTIVE · Дата: 2026-07-15 · Основание: решение Рахима 2026-07-15, ревизия ADR-0005.
> Контекст: появился первый клиент; SMS-шлюз требует юрлица и альфа-имени (отложено), поэтому
> **email становится главным каналом** доставки одноразовых кодов. Телефонный канал (SMS)
> сохраняется в архитектуре и коде, но до подключения шлюза работает только в dev (console).
> Пароль ОСТАЁТСЯ как способ входа председателя (email+пароль) — вместе со всеми парольными
> функциями админки (временный пароль при создании председателя, сброс пароля, REQ-112).

## 1. Идентификатор входа (REQ-005)

Одно поле «Телефон или email». Разбор — `parseIdentifier()`:
- строка содержит `@` → **email** (trim + lowercase, базовая проверка формы `x@y.z`);
- иначе → **телефон** (`normalizeKzPhone`, как сейчас).

Канал доставки кода следует из типа идентификатора: email → письмо, телефон → SMS.
Никакого выбора канала пользователем нет.

## 2. Флоу входа (REQ-005/006)

1. Пользователь вводит идентификатор → `POST /api/auth/otp/request { identifier }`.
2. Сервер: rate-limit (по идентификатору + IP, NFR-054 — без изменений) → создаёт
   `OtpChallenge(identifier, channel)` → шлёт код (письмо/SMS).
3. Ответ всегда `{ sent: true }` — сервер не раскрывает, существует ли аккаунт (REQ-008).
4. Пользователь вводит код → `POST /api/auth/otp/verify { identifier, code }` → при успехе
   создаётся сессия. **Первый вход создаёт пользователя** (upsert по email или телефону) —
   как и сейчас с телефоном: доступа к данным это не даёт (RLS/роли), привязку к квартире
   делает председатель.
5. Ссылка «Вход по паролю» (для председателей) ведёт на существующую форму email+пароль —
   без изменений.

## 3. Регистрация (REQ-007)

`/register` — карточки «Житель» и «Председатель» перестают быть заглушками. Обе ветки —
тот же OTP-флоу §2 (email или телефон), различие ТОЛЬКО в онбординге после входа:
- **Председатель** → `/app`, где пользователь без ролей видит форму «Создать ОСИ»
  (существующий флоу Q-051) — создав ОСИ, становится CHAIRMAN.
- **Житель** → `/app`, экран пользователя без ролей дополняется блоком «Как подключиться»:
  «Сообщите председателю ваш email/телефон — он привяжет вас к квартире». Роль появится,
  когда председатель добавит жителя (REQ-013).
- **Мастер** — существующая ветка, без изменений.

Роль НЕ хранится как выбор при регистрации — она возникает из действий (создал ОСИ /
привязан председателем / подал анкету мастера). Выбор карточки задаёт только сценарий UI.

## 4. Приглашение жителя по email (ревизия REQ-013)

Председатель добавляет жителя, указав **телефон И/ИЛИ email** (минимум один; сейчас —
только телефон). Пока SMS не подключён, приглашение по email — единственный рабочий путь
в проде. `User.phone` и `Occupant.phone` становятся опциональными (email-only аккаунты).

## 5. Модель данных (миграция)

- `OtpChallenge.phone` → `identifier` (email в lowercase или нормализованный телефон);
  новое поле `channel OtpChannel (SMS | EMAIL)`. Хеш кода — как раньше:
  `sha256(identifier:code)`.
- `users.phone` → nullable (уникальность сохраняется, NULL-ы не конфликтуют).
- `occupant.phone` → nullable.
- `users.email` — уже есть (unique, nullable), изменений не требует.

## 6. Почтовый транспорт

`src/lib/email.ts` по образцу `sms.ts`: `EMAIL_PROVIDER = console | smtp`.
- `console` (dev/тесты): письмо печатается в лог сервера, `devCode` отдаётся в ответе
  только при `OTP_DEV_ECHO=1` (та же защита, что у SMS).
- `smtp` (прод): nodemailer, env: `SMTP_HOST/SMTP_PORT/SMTP_USER/SMTP_PASS/MAIL_FROM`.
  Провайдер — транзакционный сервис (Resend/Brevo/…), решается при деплое.

Data residency (NFR-001): письмо содержит ТОЛЬКО одноразовый код — без ПДн, без содержимого
приложения (та же позиция, что для SMS в ADR-0005 и web push в REQ-105).

**Прод-гард телефонного канала:** пока `SMS_PROVIDER=console`, запрос кода на телефон в
продакшене (`NODE_ENV=production`, `OTP_DEV_ECHO≠1`) отклоняется с 503 «Вход по SMS временно
недоступен — используйте email» — иначе пользователь ждал бы SMS, которое ушло в лог сервера.
Гард снимается сам собой при переключении `SMS_PROVIDER=mobizon` (см. §6а).

## 6а. SMS-транспорт (Q-030 решён 2026-07-18)

`src/lib/sms.ts`: `SMS_PROVIDER = console | mobizon`.
- `console` (dev/тесты): как у email — код в лог сервера, `devCode` только при `OTP_DEV_ECHO=1`.
- `mobizon` (прод): Mobizon.kz, `POST api.mobizon.kz/service/Message/SendSmsMessage`,
  env: `MOBIZON_API_KEY`. Родной `fetch`, без npm-зависимости (в отличие от email/nodemailer).

Выбор провайдера и режима — по разведке 2026-07-18, отменяет предпосылку решения 2026-07-15
(«SMS ждёт юрлицо»): у Mobizon есть режим **общей подписи отправителя** (параметр `from` не
передаётся) — доставка работает СРАЗУ после регистрации аккаунта, юрлицо и альфа-имя не
требуются, SMS по казахстанским номерам с общей подписью бесплатны. Именная подпись
(«Fixly» вместо обезличенного отправителя) — отдельный апгрейд позже: нужны уставные
документы юрлица + ~10 рабочих дней регистрации у операторов связи. На работу входа
переход на именную подпись не влияет — меняется только визуальное представление отправителя.

Data residency: то же ограничение, что у email (§6) — сообщение содержит ТОЛЬКО код.

## 7. Совместимость

- API принимает и legacy-поле `{ phone }` (маппится в identifier) — на время перехода.
- e2e-теsty используют testid `phone-input`/`request-otp`/`dev-code`/`code-input`/`verify-otp`
  на единой форме — селекторы сохраняются, форма принимает и телефон, и email.
- Существующие пользователи с телефоном входят как раньше (dev) — их challenge получает
  `channel=SMS`.

## 8. Вне рамок

- Именная подпись отправителя SMS («Fixly» вместо общей) — ждёт юрлица (устав, справка eGov,
  приказ о руководителе) + регистрацию у операторов (~10 раб. дней). Когда документы будут
  готовы — добавить параметр `from` в тело запроса Mobizon (`sms.ts`), сейчас не передаётся.
- Смена/подтверждение email в профиле; восстановление доступа при утере почты — по мере
  надобности.
- 2FA/комбинации факторов — не планируются (решение 2026-07-15).
