# Спека: Telegram-канал OTP для телефона (REQ-009)

> Статус: ACTIVE · Дата: 2026-07-18 · Основание: решение Рахима 2026-07-18 (после блокера
> Mobizon — реальный SMS-шлюз в Казахстане требует ИП/юрлица у ЛЮБОГО провайдера, включая
> международных — Twilio/Vonage не решают проблему, см. mvp-build-state). Контекст: email —
> рабочий канал (auth-email.md), SMS — заблокирован до оформления ИП. Telegram закрывает
> разрыв для жителей БЕЗ email, которые предпочли бы телефон.

## 1. Модель безопасности (важнее всего в этой спеке)

Наивный дизайн «прислать код через deep-link с телефоном в URL» **небезопасен**: кто угодно
может открыть `t.me/bot?start=<чужой_телефон>` и привязать номер жертвы к СВОЕМУ чату — тогда
настоящие коды входа жертвы будут уходить атакующему (угон аккаунта).

**Правильный примитив — кнопка Telegram «Поделиться номером»** (`request_contact: true` в
reply-клавиатуре бота, Bot API). Telegram технически не позволяет через эту кнопку поделиться
чужим номером — она всегда шлёт боту номер ТЕКУЩЕГО аккаунта, из которого нажата кнопка. Это
и есть доказательство владения телефоном, эквивалентное вводу кода из SMS, но без SMS.
Следствие: **никакой подписанный токен не нужен** — привязка происходит целиком внутри
диалога с ботом, без параметров в deep-link.

## 2. Флоу привязки (одноразово, на телефон)

1. Житель открывает бота (по ссылке `t.me/<bot_username>`, статичная ссылка, без параметров).
2. Пишет `/start` → бот отвечает приветствием + клавиатурой с одной кнопкой
   «📱 Поделиться номером» (`request_contact: true`).
3. Нажимает кнопку → Telegram сам прикладывает номер аккаунта пользователя к сообщению
   (`message.contact.phone_number`) — подделать нельзя.
4. Бот получает `contact`, нормализует номер (`normalizeKzPhone`), делает
   `upsert TelegramLink(phone, chatId)`, отвечает «Готово, возвращайтесь на сайт/в
   приложение и введите этот же номер».

## 3. Флоу входа (после привязки — не отличается от SMS/email для пользователя)

1. `POST /api/auth/otp/request { identifier: "<телефон>" }` — как обычно.
2. Сервер (при `PHONE_OTP_CHANNEL=telegram`): ищет `TelegramLink` по номеру.
   - **Не найден** → НЕ создаёт `OtpChallenge` (нечего слать), не тратит rate-limit-слот
     кода. Отвечает `{ needsTelegramLink: true, telegramBotUsername }`. Сайт показывает
     экран «Откройте Telegram-бота → «Поделиться номером» → вернитесь и нажмите ещё раз».
   - **Найден** → канал `TELEGRAM`, `OtpChallenge` создаётся как обычно, код уходит
     `sendMessage` в `chatId`. Дальше — идентичный `/api/auth/otp/verify` (REQ-005/006).
3. Повторные входы того же номера — без повторной привязки (та же логика, что email/SMS).

## 4. Разграничение с SMS (REQ-030, обратная совместимость)

Новая переменная `PHONE_OTP_CHANNEL: "sms" | "telegram"`, дефолт **`sms`** — существующее
поведение (включая прод-гард 503 «Вход по SMS временно недоступен», auth-email.md §6, все
текущие e2e на `SMS_PROVIDER=console`) **не меняется**, пока флаг не выставлен явно. Когда
Рахим оформит ИП и Mobizon заработает — просто вернуть `PHONE_OTP_CHANNEL=sms` (или не
трогать вовсе, если Telegram лучше зайдёт как постоянный канал — решать по факту использования).

`OtpChannel` (enum, `OtpChallenge.channel`): добавляется значение `TELEGRAM` рядом с
`SMS`/`EMAIL` — тот же durable rate-limit-журнал (NFR-054), та же одноразовость и TTL.

## 5. Модель данных

`TelegramLink` — identity-таблица (ВНЕ RLS, как `FcmToken`/`PushSubscription`): нужна ДО
того, как известен `osi_id`, и не привязана к конкретному тенанту.

```
model TelegramLink {
  id        String   @id @default(dbgenerated("gen_random_uuid()")) @db.Uuid
  phone     String   @unique  // normalizeKzPhone, тот же формат, что identifier у OtpChallenge
  chatId    String   @map("chat_id")
  createdAt DateTime @default(now()) @map("created_at")
  @@map("telegram_link")
}
```

Без `userId`: привязка живёт по номеру телефона (как `OtpChallenge.identifier`), User может
ещё не существовать на момент привязки (первый вход создаёт аккаунт, auth-email.md §3).

## 6. Транспорт (`src/lib/telegram.ts`, по образцу `sms.ts`/`email.ts`)

- `TELEGRAM_PROVIDER: "console" | "bot"`, дефолт `console` (dev/тесты — в лог, сеть не
  трогаем, как остальные каналы).
- `sendTelegramMessage(chatId, text)` — `POST api.telegram.org/bot<TOKEN>/sendMessage`.
- `sendTelegramRequestContact(chatId)` — то же с клавиатурой запроса контакта (для `/start`).
- `handleTelegramUpdate(update)` — бизнес-логика вебхука: `/start` → клавиатура;
  `message.contact` → upsert `TelegramLink` + подтверждение. Тестируется без сети — просто
  вызывается с синтетическим Update.

## 7. Вебхук (`POST /api/telegram/webhook`)

Telegram шлёт сюда апдейты. Проверка подлинности — заголовок
`X-Telegram-Bot-Api-Secret-Token` (сверяется с `TELEGRAM_WEBHOOK_SECRET`, задаётся при
регистрации вебхука через `setWebhook`). Без секрета в проде — 401. Роут без сессии
(Telegram — не наш пользователь), без RLS (вся работа — identity-уровня).

Регистрация вебхука у Telegram (`setWebhook`) — ручной шаг ПОСЛЕ получения токена бота и
публичного HTTPS-адреса (домен/VPS либо ngrok для локальной проверки, как уже практиковалось
в проекте для Flutter web). Не входит в объём кода — команда/curl в deploy.md при подключении.

## 8. Вне рамок этой спеки

- Экран привязки Telegram в приложении (Flutter) — сайт первым, приложение — при спросе
  (сейчас приоритет сайта, первый клиент заходит через веб-регистрацию).
- Алфавитная подпись/бренд бота — не требуется, это не SMS-альфа-имя.
- Групповые чаты / несколько номеров на один `chatId` — не ограничиваем искусственно, но и
  не проектируем: `phone` уникален, `chatId` — нет (один Telegram-аккаунт теоретически может
  быть привязан к нескольким телефонам, например членам семьи без своего Telegram).
