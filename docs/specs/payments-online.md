# Спека: Онлайн-оплата жителем (демо-режим)

> Статус: DRAFT · Дата: 2026-07-14
> Контекст: REQ-030 фиксирует «эквайринг вне MVP» — это решение не пересматривается.
> Данная спека описывает **симулятор оплаты**, не реальный эквайринг: без реальных карт,
> без банка-эквайера, без ПДн платёжных реквизитов. Поэтому не запускает Q-039/юридический
> трек (vision.md §5 примечание) — это UX/демо-фича, не платёжная интеграция.

## 1. Зачем

Витрина «К оплате» в кабинете жителя ([payments/page.tsx](../../src/app/app/payments/page.tsx))
уже показывает долг и кнопку «Оплатить онлайн», но по клику — заглушка
([PayOnlineButton.tsx](../../src/app/app/_components/PayOnlineButton.tsx)): «Онлайн-оплата
скоро». Для демонстраций председателям (полевая валидация, needs.md §0.3) нужен рабочий флоу
оплаты end-to-end, даже без реального банка — это снимает главное возражение «а как жители
будут платить» на демо-встрече.

## 2. Что делает

Житель на вкладке «Платежи» видит текущий долг (`totalDebt` = сумма долга по всем трём
бакетам — `MAINTENANCE` + `TARGETED` + `CAPITAL_REPAIR`, REQ-024). Нажимает «Оплатить
онлайн» → открывается нижняя шторка:

1. Предупреждение: «Приложение работает в демонстрационном режиме. Ввод реальных банковских
   карт не требуется.»
2. Выбор способа: «Картой» или «QR (Kaspi)» — только косметический выбор, не влияет на логику,
   сохраняется как читаемая пометка в `Payment.method`.
3. Кнопка «Оплатить {сумма} ₸» → индикатор загрузки → результат:
   - успех — экран с зелёной галочкой;
   - отказ симулятора («Недостаточно средств (демо)») — можно повторить.

## 3. Что оплачивается (решение, закрывает открытый вопрос)

**Оплате подлежит весь текущий долг жителя** (сумма долга по всем трём бакетам сразу), не
отдельная «счёт-строка», как в исходном черновике ТЗ (там — оплата одного `invoice_id`).
Причина: в модели ОСИ единица начисления — `Charge` (много строк на месяц/статью), а не
единый «счёт»; экран уже показывает и продаёт идею одной суммой («К оплате: X ₸»). Оплата по
одному бакету/начислению — не нужна для демо-цели этой фичи, можно добавить позже отдельной
спекой, если понадобится.

Долг **всегда пересчитывается на сервере** в момент оплаты (Σ начислений − Σ платежей по
каждому бакету, как в `accountBalances`) — сумма из клиента не принимается. Это исключает
манипуляцию суммой с фронта и делает повтор запроса (двойной клик, две вкладки) безопасным:
если долг уже погашен предыдущим вызовом, второй вызов — no-op (REQ-034).

## 4. Симулятор эквайринга

`payOnlineDemo(osiId, userId, method, expectedAmount?)` в `src/lib/finance/service.ts`:

1. Находит `Account` жителя через `Occupant` (как `residentBalances`) и сразу пересчитывает
   долг по бакетам. Если долг = 0 — возвращает `{ success: true, alreadyPaid: true }` без
   побочных эффектов (идемпотентность, REQ-034).
2. Если передан `expectedAmount` (сумма, которую жителю показали при открытии шторки) и она не
   совпадает с реальным долгом — например, председатель успел провести другой платёж, пока
   шторка была открыта, — возвращает `{ success: false, reason: "amount_changed",
   currentAmount }` **без** списания. Это защита от тихого списания другой суммы, чем ту, на
   которую жителю показали кнопку «Оплатить X ₸» (REQ-036, ревизия после code review 2026-07-14).
3. Имитирует задержку сети ~1.5 c (реалистичность, как в исходном ТЗ).
4. С вероятностью 5% возвращает симулированный отказ («недостаточно средств») — данные не
   меняются (REQ-036).
5. При успехе — **одна транзакция** (`forTenant`), внутри которой долг перечитывается заново
   (мог измениться за время задержки — если он уже 0, тоже `alreadyPaid: true`) и создаётся по
   одному `Payment` на каждый бакет с долгом > 0 + запись в `AuditLog` (REQ-090) + пересчёт
   статусов `Charge`. Все бакеты списываются атомарно — либо все, либо ни одного (ревизия: раньше
   каждый бакет уходил через отдельный вызов `addPayment()` со своей транзакцией — при падении
   между вызовами долг мог оказаться погашен частично). `incomeCategory` для бакета фиксирован:
   `MAINTENANCE` → `RESIDENT_DUES`, `TARGETED` → `TARGETED_RESIDENT`, `CAPITAL_REPAIR` →
   `CAPITAL_REPAIR_CONTRIBUTION` (варианты «парковка»/«аренда» недоступны онлайн-жителю — это
   ручной ввод председателя для прочих случаев).
6. `Payment.method` = `"Тест: картой"` / `"Тест: QR"`. `Payment.gatewayRef` = `TEST-TX-XXXXXX`
   (аналог `payment_gateway_ref` из исходного ТЗ) — чисто информационная метка для «истории
   платежей», не используется для идемпотентности (её обеспечивает пересчёт долга, п.1/5).

### Гонка при двойном клике — сужена, не устранена полностью

Долг читается **дважды**: один раз до имитационной задержки (шаг 1, для проверки
`expectedAmount`/`alreadyPaid` без траты времени на заведомо неудачный кейс) и один раз заново
внутри финальной транзакции **после** задержки (шаг 5) — именно от повторного чтения зависит
факт списания. Поэтому окно гонки для двух параллельных запросов — это время одной транзакции
(создание нескольких строк `Payment` + пересчёт статусов), а не вся 1.5-секундная задержка, как
было до ревизии 2026-07-14. Полностью гонка не устранена (`forTenant` не даёт `SELECT ... FOR
UPDATE` на строки счёта) — для демо-функции без реальных денег это принимается: `accountBalances`
считает `debt = max(0, charged - paid)`, так что худший случай — не отрицательный долг, а
«переплата», видная в истории платежей. Если фича перерастёт демо-статус (реальный эквайринг,
ADR-0010), блокировку строк нужно будет добавить.

## 5. API

`POST /api/payments/checkout` — доступ: `memberContext()` (житель, member активной ОСИ), вход
`{ method: "test_card" | "test_qr", expectedAmount?: number }`. Подробности — `api-contracts.md`.

## 6. Вне рамок этой спеки

- Оплата отдельного бакета/начисления выборочно.
- Реальный эквайринг/Kaspi Pay API — остаётся REQ-030 (вне MVP).
- Уведомление жителю об успешной оплате (Notification/Push) — не запрашивалось, можно добавить
  отдельной спекой поверх существующего REQ-101, если понадобится.
