# Спека: Маркетплейс заявок — мастера (модуль «Мастер»)

Статус: черновик на утверждение (2026-07-04). Архитектура — ADR-0009 (витрина, не BYPASSRLS).
Референсы UX: YouDo / Profi / Uslugi.kz (лента заказов города → отклик → договорённость).

Решения Рахима (зафиксированы): публикует председатель; мастера только проверенные;
ПДн жителя скрыты до принятия отклика.

## 1. Роли и сущности

- **Master** (identity-слой, вне RLS): userId (общая таблица User — вход телефон+OTP),
  fullName, city, специализации (категории RequestCategory[]), о себе,
  status: PENDING | APPROVED | REJECTED | BLOCKED. REQ-060.
- **MarketListing** (витрина, ADR-0009): id, osiId+requestId (скрытые служебные),
  city, category, title (маскированный), description, photoUrls, buildingLabel
  («ул. Абая, 1» — дом без квартиры), status: PUBLISHED | TAKEN | CLOSED,
  publishedAt. RLS: PUBLISHED читают APPROVED-мастера своего города. REQ-061.
- **MarketOffer** (отклик): listingId, masterId, message, price? (₸, опционально),
  status: OFFERED | ACCEPTED | DECLINED | WITHDRAWN. Мастер видит свои,
  председатель — отклики своих листингов. REQ-062.

## 2. Флоу

1. **Публикация (председатель)**: на заявке дома кнопка «Опубликовать мастерам» →
   форма-предпросмотр (что увидят мастера: заголовок/описание можно поправить, фото
   отметить галочками) → MarketListing PUBLISHED. Кнопка «Снять с публикации». REQ-063.
2. **Лента мастера** `/master`: карточки заказов его города (+фильтр по категории):
   категория-иконка, заголовок, описание, фото, дом/район, «N откликов». БЕЗ квартиры
   и контактов. REQ-064.
3. **Отклик**: «Откликнуться» → сообщение + (опц.) ориентировочная цена → OFFERED.
   Председатель получает уведомление (существующий notify()). REQ-065.
4. **Принятие (председатель)**: список откликов на заявке → «Принять» одного →
   этот OFFER = ACCEPTED, остальные DECLINED, листинг = TAKEN. Мастеру раскрываются
   квартира и телефон контакта (эндпоинт проверяет ACCEPTED — ADR-0009). Уведомления
   обоим. Дальше договариваются напрямую (телефон/WhatsApp); тред заявки остаётся
   каналом председатель↔житель. REQ-066.
5. **Завершение**: председатель закрывает заявку как сейчас (RESOLVED) → листинг CLOSED.
   Отзывы/рейтинги мастеров — Фаза 2 модуля, вне MVP. REQ-067.

## 3. Верификация мастеров (REQ-068)

Регистрация: `/register` → роль «Мастер» (расширяем текущую заглушку) → телефон+OTP,
анкета (ФИО, город, категории) → PENDING → экран «Профиль на проверке».
Одобрение: до админки (ADR-0008) — вручную суперадмином (скрипт `scripts/approve-master.ts`).
Q-053. APPROVED открывает ленту. BLOCKED — скрывает всё.

## 3а. Обязательное правило сервисного слоя (M4, из ревизии M1 2026-07-05)

RLS-политика `master_own` на `market_offer` проверяет ТОЛЬКО `master_id = current_master_id`
(см. ADR-0009) — `osi_id` в контексте мастера НЕ участвует ни в одной проверке. Это значит:
**сервисная функция создания отклика обязана брать `osiId` из уже прочитанного листинга
(`listing.osiId`), а НЕ из клиентского ввода.** Иначе мастер может подставить чужой `osiId` в
`MarketOffer.osiId`, и председатель другой ОСИ увидит через `forTenant` посторонний отклик
(данные не приватные, но нарушение изоляции тенантов — обрабатывать как баг, не только как UX).
Паттерн: `const listing = await tx.marketListing.findFirst({ where: { id, status: 'PUBLISHED', city } }); if (!listing) throw notFound; tx.marketOffer.create({ data: { osiId: listing.osiId, ... } })` — всё в одной `forMaster`-транзакции.

## 4. Приватность (REQ-069, критично)

В витрину копируются ТОЛЬКО: категория, отредактированный председателем текст, фото
(отмеченные), адрес дома. НИКОГДА: квартира, ФИО/телефон жителя, тред заявки.
Раскрытие после ACCEPTED: квартира + телефон контакта (председателя или жителя — выбирает
председатель при принятии). Мастер НЕ входит в тенант: у него нет forTenant-контекста.

## 5. Предпосылки и порядок работ

- **M1** — модель: Master, MarketListing, MarketOffer, `Building.city` + `Master.city`
  (структурированный город; бэкфилл существующих домов — «Кокшетау» по умолчанию),
  RLS-политики витрины + integration-тест изоляции (мастер чужого города / PENDING /
  не видит ПДн). Миграция.
- **M2** — регистрация и верификация мастера (+скрипт одобрения). UI «на проверке».
- **M3 готов (2026-07-05)** — фото-аплоад: `POST /api/uploads` (sharp: resize≤1600px,
  webp q82, EXIF/GPS стирается перекодированием), лимиты 5 файлов × 5МБ, тип
  jpeg/png/webp; `src/lib/uploads/service.ts`; хранение — `public/uploads/` (локальный volume
  `docker-compose.yml`, data-residency РК, Q-054); `PhotoUpload.tsx` подключён в `RequestForm`,
  миниатюры — в `RequestCard`. ⚠️ Dockerfile: `COPY ... /app/public` ТРЕБУЕТ
  `--chown=nextjs:nodejs` (иначе смонтированный volume недоступен для записи непривилегированным
  пользователем рантайма — исправлено в этом срезе).
- **M4 готов (2026-07-05)** — `src/lib/market/service.ts` (publishListing/unpublishListing/
  listOffersWithMasters/acceptOffer — forTenant; listCityListings/listMyOffers/createOffer/
  withdrawOffer — forMaster) + API `/api/market/listings[/[id]/unpublish]`,
  `/api/market/offers/[id]/accept`, `/api/master/listings/[id]/offers`,
  `/api/master/offers/[id]/withdraw`. UI: `MarketplacePanel` в `RequestCard` (только
  `/app/buildings/[id]/requests`) — публикация с предпросмотром (заголовок/описание/выбор фото),
  список откликов, «Принять» → раскрывает телефон мастера (`OfferWithMaster.phone` только при
  ACCEPTED). `/master` (APPROVED) — вкладки «Заказы»/«Мои отклики», `RespondToListing`,
  `WithdrawOfferButton`. Проверено вручную сквозным флоу публикация→отклик→принятие→раскрытие
  контакта (через preview) + unit/integration/e2e зелёные.
- **M5 готов (2026-07-05)** — `e2e/marketplace.spec.ts`: полный флоу публикация → регистрация
  мастера → ручное одобрение (execSync scripts/approve-master.ts, как в проде) → отклик →
  принятие → раскрытие контакта, плюс явные негативные проверки приватности (ФИО/телефон/номер
  квартиры жителя НЕ встречаются на страницах мастера ни до, ни после принятия). По пути найден
  и исправлен реальный баг: после принятия отклика (TAKEN) политика `market_read` переставала
  пускать мастера к ЕГО ЖЕ листингу — «Мои отклики» показывали «Заказ закрыт». Исправлено
  миграцией `20260705101619_market_read_own_offers` (условие «или есть свой отклик на этот
  листинг» через EXISTS-подзапрос к market_offer) + новый integration-тест на это поведение.

Вне MVP модуля: рейтинги/отзывы, комиссия (Q-055), чат мастер↔житель в приложении,
самостоятельная публикация жителем.

## 6. Мобильный клиент (срез 25, добавлено 2026-07-19)

Ревизия при реализации build-plan-3-unification.md среза 25: разведка кода перед стартом
показала, что веб-модуль M4 отдаёт `listCityListings`/`listMyOffers` только в серверный
компонент `web/src/app/master/page.tsx` — JSON-эндпоинтов для мобильного клиента нет.
Не хватает трёх GET-роутов (REQ-148..150). Заодно зафиксированы два сокращения объёма
относительно клетки «25» в build-plan-3 §12а — оба вытекают из уже принятых решений этого же
модуля, не новые ограничения:

- **REQ-148** [MUST] — `GET /api/master/me` (auth: `getCurrentAuth()`, как `/api/master/register`,
  не `masterContext()` — самому мастеру нужно узнать СВОЙ статус, включая PENDING/REJECTED/
  BLOCKED, когда `masterContext()` уже отказал бы). Ответ: `{ master: { id, status, city,
  categories, fullName, bio } | null }`. Закрывает пробел: `POST /api/master/register` — это
  «выстрелил и забыл», у приложения нет способа перепроверить статус после перезапуска
  (сравни со сплэшем, который всегда перепроверяет сессию через `/api/auth/me`).
- **REQ-149** [MUST] — `GET /api/master/listings` (auth: `masterContext()`) — JSON-обёртка
  над `listCityListings(masterId, city)`. Ответ: `{ listings: MarketListing[] }`.
- **REQ-150** [MUST] — `GET /api/master/offers` (auth: `masterContext()`) — JSON-обёртка над
  `listMyOffers(masterId, city)`. Ответ: `{ offers: (MarketOffer & { listing:
  MarketListing | null })[] }`.

**Сокращение 1 — «история заработка» → «Мои отклики» без денежной агрегации.** У
build-plan-3 срез 25 унаследовал формулировку «история заработка мастера» из старого
`income_screen.dart` (Supabase, агрегировал `tasks.final_price` по завершённым заказам).
В модели этого модуля НЕТ подтверждения оплаты и НЕТ обязательного `price` — `MarketOffer.price`
опционален и это ориентировочная цифра из отклика, не факт оплаты (§2 п.4: «договариваются
напрямую», раздел «Вне MVP» уже исключает комиссию/монетизацию). Строить график «дохода» не
из чего — заголовок ввёл бы в заблуждение (выглядел бы как подтверждённые деньги). Мобильный
экран показывает свои отклики со статусами (OFFERED/ACCEPTED/DECLINED/WITHDRAWN) и
опциональной ценой из отклика, той же вкладкой «Мои отклики», что уже есть на сайте
(`web/src/app/master/page.tsx`) — не новый функционал, только перенос существующего.

**Сокращение 2 — без чата и без «треда заявки» для мастера.** Обе строки в клетке «25»
build-plan-3 конфликтуют с уже принятым в этом модуле: чат мастер↔житель прямо в разделе «Вне
MVP» выше, а «тред заявки» мастеру структурно недоступен — ADR-0009 сознательно не даёт мастеру
доступ к `Request`/`RequestMessage` вообще, только к обезличенной проекции `MarketListing` +
раскрытию телефона после ACCEPTED (§4). Канал общения после принятия — прямой звонок
(`tel:`), как уже было в старом `order_details_page.dart` через `url_launcher`, не новый чат.
