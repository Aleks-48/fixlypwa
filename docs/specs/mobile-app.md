# Спека: мобильное приложение (fixly) — переход на единый бэкенд

> Статус: ACTIVE · Дата: 2026-07-16 · Основание: ADR-0011, ADR-0012, решения Рахима
> 2026-07-16, `docs/build-plan-3-unification.md`.

## 1. Что это

`fixly` (`C:\Projects\fixly`) — нативное Flutter-приложение (Android/iOS/desktop),
реализующее тот же домен ОСИ, что и сайт, но сейчас на Supabase Cloud. Эта спека описывает
переход приложения на API `fixlypwa` без переноса данных (ETL отменён — в проде Supabase
только тестовые учётки).

Экраны и UX **сохраняются** — задача не «переписать приложение», а заменить его слой
данных. Что откуда в приложении убирается или добавляется на время перехода — раздел 4.

## 2. Роли: разделение сайт / приложение

Согласно решению Рахима (2026-07-16): **сайт = председатель + админ, приложение =
житель + мастер.** Обе роли аутентифицируются в одной системе (`User`, `UserOsiRole`,
`Master` — без изменений схемы), различие только в том, какой клиент какую роль обслуживает
по умолчанию.

- **REQ-120** [MUST] — Мобильный клиент аутентифицирует жителя (`Role.RESIDENT`) и мастера
  (`Master`, identity вне RLS, ADR-0009) тем же способом входа, что и сайт: email-код или
  пароль (ADR-0005 ревизия 2026-07-15). Председатель и суперадмин продолжают пользоваться
  сайтом; мобильный вход для них не проектируется в рамках этой спеки.
- **REQ-121** [SHOULD] — ⚠️ **Ревизовано 2026-07-17** (запрос Рахима, onboarding-unified.md
  §3/REQ-143..145): председателю доступны ОПЕРАТИВНЫЕ функции в приложении (заявки дома,
  объявления, уведомления — свой шелл), управление (финансы, отчёты, реестр, импорт) — на
  сайте. Старые chairman-экраны fixly по-прежнему не портируются — интерфейс строится новый.

## 3. Транспорт и авторизация (ADR-0012 §1)

- **REQ-122** [MUST] — `GET /api/auth/me` и все защищённые роуты принимают сессионный
  токен через заголовок `Authorization: Bearer <token>` как альтернативу cookie
  `osi_session`. Модель `Session` (TTL, `activeOsiId`, инвалидация) не меняется —
  меняется только точка чтения токена в `getCurrentAuth()`.
- **REQ-123** [MUST] — `POST /api/auth/login` и `POST /api/auth/otp/verify` (либо
  email-код эквивалент, ADR-0005 ревизия) при заголовке `X-Client: mobile` возвращают токен
  и `expiresAt` в теле JSON-ответа вместо установки cookie. Формат заголовка/флага —
  уточняется при реализации среза 19, не блокирует спеку.
- **REQ-124** [MUST] — Flutter хранит токен в защищённом хранилище устройства
  (`flutter_secure_storage` или аналог), не в открытом виде.

## 5. Push-уведомления (ADR-0012 §5)

- **REQ-127** [MUST] — Новая identity-таблица `FcmToken` (вне RLS, по образцу
  `PushSubscription`): `userId`, `token`, `createdAt`. `POST /api/push/fcm-token` —
  регистрация токена мобильного клиента.
- **REQ-128** [MUST] — `notify()` (срез 7) при создании `Notification` доставляет и через
  Web Push (существующий путь), и через FCM (`firebase-admin`), независимо и без взаимной
  блокировки — сбой одного канала не должен ронять другой.
- **REQ-129** [MUST] — FCM, как и VAPID, graceful-off без настроенных ключей (тот же
  паттерн, что уже принят для Web Push) — приложение и API не падают без `FIREBASE_*` env.
- **REQ-130** [MUST] — Мёртвые FCM-токены (ошибка `UNREGISTERED`/`INVALID_ARGUMENT` от
  Firebase) удаляются автоматически — по аналогии с REQ-103.

## 6. Файлы

- **REQ-131** [MUST] — Все загрузки из мобильного клиента (фото заявок, аудио-сообщения)
  идут через `/api/uploads`: загрузка только авторизованная (MIME-контроль, EXIF-зачистка),
  чтение — по непубликуемой UUID-ссылке (obscurity-модель MVP, ADR-0012 §3 в ред. 2026-07-16;
  полная приватная отдача — за Q-054). Аудио-вложения требуют расширения `/api/uploads`
  (сейчас только изображения) — входит в срез 22 вместе с голосовыми сообщениями.
  Закрывает Q-060.

## 7. Реалтайм (ADR-0012 §2)

- **REQ-132** [SHOULD] — До реализации SSE (срез 24) мобильный клиент использует
  pull-to-refresh / поллинг для списков заявок, чата, объявлений — временная мера, не
  финальная архитектура.
- **REQ-133** [SHOULD] — После среза 24: список заявок, тред заявки, лента объявлений,
  центр уведомлений подписываются на `/api/events` (SSE) вместо поллинга.
